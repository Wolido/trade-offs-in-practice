# 《把日期写进系统提示词》— 位置决定代价

想让智能体知道今天几号，是个朴素的需求：问它"今天星期几"，让它判断"这个任务还剩几天"，或者生成带日期的报告，都要求模型对当前日期有数。模型自己没有日历，**最直接的办法是在系统提示词里写一行日期**。

但日期是动态内容。[《什么是缓存命中》](./what-is-cache-hit.md)和[上一篇《为什么缓存命中率差异巨大》](./cache-hit-rates-differ.md)建立的纪律是：把不变的钉在提示词开头，动态的放尾部。上一篇把"当前日期"当成动态内容的典型反面例子，给过示意数字：在系统提示词开头塞一个跨天变化的日期，命中率约 2%。**把日期写进系统提示词之前，先想清楚它放在哪个位置**，同一行日期，放在开头和放在尾部，代价差别巨大。

## pi 的先例

我用 [pi](https://github.com/earendil-works/pi-mono) 干活，查资料时发现这件事有个现成的官方先例。pi 的默认系统提示词里曾经就有一行 ISO 格式的当前日期，**后来在 0.80.7 版本被专门移除，CHANGELOG 写明的理由是修复跨日期的系统提示词缓存失效**，修法是从默认提示词里删掉日期（[#6621](https://github.com/earendil-works/pi/issues/6621)）。

失效发生在提示词被重新生成的时刻：reload、恢复旧会话、跨天之后新开会话，默认提示词重新生成，日期更新，前缀在日期处多出一个变化点。官方愿意为一个日期发一次修复，可见这个失效在他们眼里值得动手。

官方同时留着一个通用入口，正好能用来把日期加回来。pi 的`--append-system-prompt`参数接受内联文本或文件路径，可以多次使用，内容追加到系统提示词尾部稳定内容之后，其后仍可能排着项目上下文、skill 描述、当前目录行等少量静态内容（见 pi 仓库的 #114、#3171）。用它塞日期，位置天然就在尾部。

## 失效拆开算

日期引起的缓存失效，实际会发生多少次？拆成四个场景算一遍。

**同一个会话里，日期只在启动时生成一次，之后每轮请求都复用同一份文本，缓存不受影响**。 注入发生在会话开始时，之后日期变不变，提示词里的字符串都不变。附带一个正确性代价：会话挂着跨了午夜，模型眼里的日期就慢了一天。这个代价先记下，最后一起算。

对话放一夜，第二天接着用，缓存还活着吗？各家缓存的存活时间在《什么是缓存命中》里写过：Anthropic 和 OpenAI 的内存缓存以分钟计，DeepSeek 的磁盘缓存能活数小时到数天。**缓存过期是 TTL 的事，放不放日期都要面对，和日期无关**。 这类失效发生时命中率直接归零，但放不放日期都一样。

真正由日期引起的失效，只发生在提示词被重新生成的时刻：新开会话或 reload 时，日期从昨天变成今天，变化点出现。**日期变化造成的失效，一天只发生一次**，就发生在跨天后的第一批请求上：前一天攒下的缓存内容在日期处对不上，当天的新内容从此建立，接下来这一天，日期不再参与失配。

一次失效损失多少，由位置决定。上一篇给出过公式：命中率 = 匹配前缀长度 / 总输入长度，变化点之前照常命中，之后全部失配。**失配比例 = 变化点之后的长度 / 总输入长度，位置决定损失大小**。

按这个公式把两个位置摆出来算。日期在系统提示词开头：变化点之后是剩余的提示词、工具定义、全部历史，几乎整份输入失配，命中率掉到约 2%，上一篇的示意数字就是从这个位置算出来的。日期在尾部：变化点之前的所有稳定内容照常命中。**同一行日期，开头吃满整份输入的重算，尾部只吃日期后面那一小段**。

## 放末尾为什么基本没有影响

日期追加到系统提示词尾部稳定内容之后，它后面只剩少量静态内容和会话历史。**日期后面只剩少量静态内容与会话历史，而历史本来就是每轮都在重算的动态区**：每轮请求都在尾部追加新消息，新增部分每轮都要 prefill，这是 append-only 对话的天性。那些静态内容（项目上下文、skill 描述、当前目录行）只在跨天后的第一次请求失配一次，量级远小于日期之前的稳定前缀。日期每天只变一次，历史每轮都在变，日期这个每天一次的变化点，几乎贴着稳定区和动态区的交界处。

跨天后的第一次请求，具体会损失什么？分三种情况。新会话：日期后面只有少量静态内容和一条全新的用户消息，本来就没有缓存可命中，损失为零。reload 隔夜的老会话：Anthropic 和 OpenAI 的内存缓存早已过期，整段历史本来就要重算，日期没有多花一分钱。DeepSeek 的磁盘缓存还活着的窗口里，日期才多算一遍它后面的内容，一天一次。**把日期放系统提示词尾部，每天一次的变化点落在动态区近旁，额外损失趋近于零**。

这个结论有个前提：系统提示词要够大，位置才值钱。**代价与长度成正比，系统提示词越大，位置越值钱**。 如果提示词总共几百 token，全量重算也便宜，开头还是尾部无所谓，这篇分析对你没用。

## 两端

把 pi 的官方选择和我的选择并排看，是同一个 trade-off 的两端。**官方选择在默认提示词里完全不注入，我选择注入但放尾部，代价是一天一次、一次多算尾部剩下的内容**。 官方换来的是默认提示词里少一项动态内容，模型默认因此不知道今天几号。我的账本反过来：付一天一次的账，换模型知道日期。两种选择都自洽，差别只在各自愿意付什么。

中间不存在"注入但放开头"的合理选项。模型读的是整份提示词，日期放开头和放尾部，它读到的内容一模一样，放开头没有任何额外收益，只有最大的代价。真要注入，答案只有尾部。

前面记下的正确性代价，这里一起算掉：会话挂着跨午夜，模型眼里的日期会慢一天。**在我的体验里，我的会话基本活不过一天**，每天开工开新会话，日期自然刷新；偶尔跨天挂着，慢一天的日期在我的用法里也够用。

## 我的做法

实施上，官方入口是现成的。前面说过，pi 的`--append-system-prompt`接受内联文本或文件路径、可多次使用、追加到系统提示词尾部。**我打算用它把当天的日期追加到系统提示词尾部**，让模型知道今天几号，同时把变化点停在动态区边界近旁。这个计划写到这里还没落地，具体的参数写法等实测验证过再补。

回到开头的问题：想让智能体知道今天几号，该不该往系统提示词里塞日期？该塞，前提是你的系统提示词已经大到值得计较位置。塞的时候记住一句话：**位置对了，这行日期的代价小到可以忽略**。官方把日期从默认提示词里移除了，我选择把日期放在尾部，两边都是同一个问题的答案。
