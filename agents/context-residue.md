# 上下文里的"行动残渣"：为什么写操作比读操作更污染

## 观察

用智能体做项目时，我渐渐注意到一个模式。主智能体在规划阶段调用 read 类工具，读完后能很快形成判断。但一旦它开始亲自 write，状态就变了：它要处理的细节量突然暴增，而事后回头看，这些细节大部分跟它接下来的决策没什么关系。

拿规划阶段和动手阶段对比着看，差别就很清楚了。主智能体在思考"这个重构该怎么做"时，需要看几个关键文件的结构，理解模块之间的依赖。这时候它的 read 是有方向的：缺什么读什么，读完就判断。但决定"我先改一下这个文件试试"之后，情况不同了。write 要求它把整个文件内容组织好：导入语句、类定义、方法签名、注释格式，每一项都要对。它处理了几十上百行代码细节，而真正影响后续决策的，可能只是其中某几行的改动意图。

这些细节用过即废。规划阶段不需要它们，子智能体返回的摘要里也不会提。但它们已经进了上下文，占据 token，参与后续每一轮推理。

反复看到这个模式之后，我意识到一件事：**上下文增长其实分主动和被动两种**。关键区别不在于操作类型。不是说读都好、写都坏。区别在于细节以什么方式进入上下文。

## 问题

主智能体的职责是全局判断:决定做什么、分给谁、拿到结果后怎么整合。这些判断不需要全部信息。它们需要的是关键信息。但**关键细节决定全局判断的准确性**：漏掉一个模块的接口约定，规划就可能跑偏。可这些细节偏偏省不得，信息不全的时候做全局判断，出错是迟早的事。

所以真正的问题是：**细节以什么方式进入上下文**？是自己去找的，还是被动灌进来的？

## 判断

### 主动获取：read 是"我要什么才读什么"

read 类工具（读文件、搜索、列目录）有一个共同的结构特征：**调用之前，主智能体已经知道自己在找什么**。它可能不确定答案，但它确定问题。于是主动发出请求，拿到结果后筛出有用的部分，纳入自己的判断框架。

**上下文按主智能体的思路组织**。不是所有细节都进来。"我要什么"决定了"我读什么"。进来的内容对判断有用,因为没用就不会去读。

在我体验里，这个筛选只有一种情况会出问题：找错了文件，读错了文件。除此以外，read 进来的每一段内容，读的时候都有明确的理由，读完之后也确实参与判断。主智能体在主动构建自己的上下文，而不是被动接收。

### 被动获取：write 的载荷搭车进入上下文

write 类操作（写文件、编辑文件、执行命令）的情况完全不同。

上一篇《[主智能体的能力约束](./capability-constraint.md)》里提到过一个信息密度的观察：一次 write 返回"文件已写入"，有用信息五个字；一次 bash 返回几十行日志，有用的只有最后两行。那是从信息密度的角度讲的。这里我想展开另一个维度：这些东西为什么会留在上下文里。

答案不是它们有用，而是它们**跟操作绑定在一起，想甩都甩不掉**。write 天然要求主智能体处理完整的文件内容，不管它只需要改一行还是改一百行，它都得把整个文件的逻辑过一遍。edit 返回的 diff 同样把变更的上下文全带进来。bash 跑编译或测试，输出的日志一字不漏地灌进上下文。

这些载荷进入上下文，纯粹是操作本身的要求，跟决策需要无关。搭了操作的便车进来,占着位置,却不参与后续推理。

我用下来最深的感受是：这些细节看着像信息，其实更像噪音。真正有用的那部分，改了什么、为什么改，淹没在大量的实现细节里。

### 行动残渣：高占用、低价值

这些被动进入上下文的执行痕迹，我给它们起了个名字：**行动残渣**。

每次写操作都在上下文里留下一层薄薄的残留。单独看一层，微不足道。但长会话里，几十上百次操作叠在一起，残渣的量就相当可观了。更麻烦的是，残渣还有两种具体的危害。

**第一，高占用**。这是最直接的。一次 write 也许不占多少 token，但累积效应显著。长任务跑到后半段，上下文里很大比例是过往操作的痕迹，而不是当前决策需要的信息。

**第二，低价值**。残渣的信息对主智能体的规划几乎没有帮助。编译日志的完整输出、文件的历史版本内容，这些东西占着 token 预算，却不参与推理。它们在推理中被模型读了一遍又一遍，却产不出任何有用的结论。

两种危害指向同一个根源:**写操作把不需要的细节强行塞进上下文**。读操作不会这样。读是“我要什么才读什么”，进来的东西用完就过去了，不会在上下文里越积越多。

### 解法：从源头切断被动增长

想清楚这一点之后，解法很直接：**禁止主智能体的 write，从源头规避被动上下文增长**。

指望模型自觉少写靠不住。上一篇已经讨论过，上下文一长就会松动。简单说就是：从工具白名单里移除 write、edit、bash，主智能体就没有任何渠道产生行动残渣。**结构性解法，不靠自觉**。

主智能体仍然可以 read 任何文件，它需要关键细节来做全局判断，read 给了它这个能力。但所有修改系统状态的操作，一律委派给子智能体。子智能体产生的执行残渣留在子智能体自己的上下文里，不影响主智能体。

这里涉及操作颗粒度的问题。操作越细，反复越多。改一行、调一个参数、重写一个函数，每次微调都作为独立操作进入上下文，中间状态一层层叠上去。**把颗粒度放到"调用子智能体"这一级，这些中间状态就进不了主智能体的上下文了**。子智能体内部怎么反复改、怎么来回调，全封在它自己的上下文里，主智能体接触到的只是委派的结果。

但颗粒度的价值不止在隔离中间状态。它还有一个更隐蔽的好处：**硬约束让主智能体观察问题的颗粒度始终保持一致**。只读加委派，意味着主智能体永远只能看到任务级的东西：委派了什么、摘要说了什么。不管会话跑了多久、上下文攒了多长，它观察世界的粒度不会变。而亲自做 write 的智能体，观察粒度会随着细节堆积而不断下沉：起初还在思考"这个模块怎么重构"，几个文件改下来，注意力已经完全陷在函数签名和参数顺序里了。长上下文里最怕这种视角漂移，判断标准和观察方式不知不觉跟着细节一起往下沉。硬约束把观察颗粒度钉死在任务级，从头到尾不变。

目前主流智能体框架的常见做法是"下放探索、保留执行":让子智能体去读文件、搜索代码,但写文件和跑命令留给主智能体。在我的体验里,**这个方向选反了**。读操作返回高价值信息,应该留在主智能体的上下文里帮助判断;写操作产生低价值残渣,才应该被隔离出去。“下放探索、保留执行”把有用的推出去、把残渣留下来。该留在主智能体上下文里的，被推给了子智能体；该隔离出去的，反而堆在主智能体这边。方向完全反了。

## 结果与教训

禁止 write 之后，最直接的变化是：**主智能体的上下文不再被动膨胀**。它只随决策序列增长，不随执行痕迹增长。这个效果在长任务里尤其明显。上一篇已经描述过长任务跑到后期主智能体状态不退化的感受，这里不重复。

从更广的视角看，主动和被动上下文增长的区分，帮我理清了一个之前模糊的问题：为什么有些上下文"干净"，有些"脏"。干净的上下文，每段内容都是主动选择进来的。脏的上下文，大量内容是被动灌入的。

**这是一个结构性区别，跟内容多少无关**。

需要明确标注：本文的全部观察和结论来自我的个人使用体验，属一级证据。主动和被动上下文增长的区分，目前**没有人量化过 read 和 write 对上下文质量的不同影响**。这个概念在我的使用场景里有效，但它的普适性和量化边界，需要未来严格的实验来验证。我把它写出来，是希望有人能接着往下做。
