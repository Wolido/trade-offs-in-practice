# 为什么不把主上下文 fork 给子智能体

## 观察

在我的体系里，委派时子智能体拿到的背景通常只有一两句话：任务是什么、在哪个仓库、做完谁来看。更多背景它没有。子智能体经常在不了解全局约束的情况下做局部判断，出错了主智能体才发现。**子智能体只有一句话背景，这是上下文切割的代价**。切割的收益之前两篇讲过：上一篇《[上下文里的"行动残渣"](./context-residue.md)》讲了主智能体亲手写操作时低价值残渣如何污染自己的上下文；《[为什么主流框架不做硬隔离](./why-mainstream-does-not.md)》讲了这套结构在商业框架视角下的成本边界。盲区是切割的实付部分，不会因为收益成立就消失。

所以我第一次看到 [pi-subagents](https://github.com/tintinweb/pi-subagents) 的`inherit_context`功能时，觉得这就是现成的答案：把主智能体的上下文整个继承给子智能体，盲区补上，切割的代价消失。**`inherit_context` 看起来是补偿这个盲区的现成答案**。

顺着它的实现把账算下去，答案的代价在别处。本文把`inherit_context`的实现拆开，算这笔账。

## 问题

把"fork 上下文补偿盲区"转成可分析的问题，需要先弄清两件事：fork 的内容在子智能体那边以什么形式存在，这个存在形式每次委派要付出什么成本。然后才能判断补盲区的收益在什么条件下盖得过成本。

## 判断

### fork 的实现是纯文本拼接

`inherit_context` 的实现可以直接从源码看。pi-subagents 的 `buildParentContext` 把父会话渲染成一段纯文本，agent-runner 把这份文本贴在任务文本前面，作为第一条消息进入子智能体会话。

这个实现没有截断，也没有长度上限。父会话多长，渲染出来的文本就有多长，子智能体的上下文就有多大。**fork 的实现是纯文本拼接，父会话多长，子智能体的上下文就有多大**。

"继承上下文"这个说法因此容易误导。子智能体拿到的是渲染出来的文本快照，原对话里的结构信息已经丢了：哪句话是谁说的、哪次工具调用对应哪个问题，全部压扁成流水账。

### fork 的内容不在子智能体上下文的前缀上

这一笔是缓存账。上一篇《[什么是缓存命中](../dengwei/what-is-cache-hit.md)》讲过，提示词缓存按前缀精确匹配，前缀一致才命中，分歧点之后重算。**fork 的内容在子智能体的上下文里不在前缀上**，它前面压着子智能体自己的系统提示词。子智能体的请求前缀从它自己的系统提示词开始，和主智能体的前缀从第 0 个 token 就分歧，主智能体侧建立的缓存（含整个主上下文）对子智能体整体不可用。这是结构性事实，同模型也一样，异模型时 tokenizer 不同，更不可能复用。

在会话内部，fork 文本这段是稳定的。它作为第一条消息进入子智能体会话后，固定在消息历史里，成为子智能体自己稳定前缀的一部分，子智能体多轮之间的请求照常命中。

fork 文本真正的缓存损失在跨委派这一层。主上下文每次委派都不同，渲染出的 fork 文本随之不同，跨委派基本命中不了。**主上下文每次不同，fork 文本跨委派基本全价重算**。主智能体侧的缓存对子智能体永远复用不上，这笔也省不了。子智能体自己的系统提示词和工具定义跨委派稳定，这部分反而照常可命中：DeepSeek 的磁盘缓存跨会话按内容匹配，dengwei 系列写过这一点。

上一篇《[为什么主流框架不做硬隔离](./why-mainstream-does-not.md)》讲进程隔离打断主智能体自己前缀的缓存，账从主智能体进程一侧算。本文这笔账从子智能体一侧算：即使把主上下文整个搬过来，它在子智能体一侧依然换不来折扣价。

### 跨模型读历史的质量损耗

缓存账是成本问题。这一节是质量问题，也是本文最想说的点。

**模型 B 读模型 A 写的历史，质量会有损失**。先交代我的体验。我在 [pi](https://github.com/earendil-works/pi-mono) 里有多次主智能体会话中途切换模型的经历。在我的体验里，**上下文推进到约 40% 时切换模型，接手模型的输出质量明显变差**：判断变钝，经常反复确认上下文里已经写过的结论，行文风格跟整个会话的历史对不上。

我最初以为这是切换瞬间的波动，多聊几轮会恢复。实际用下来没有恢复，或者说恢复很慢。我后来把它归因于一个机制，这是我对自身体验的解释，没有做过测量：不同模型的后训练不同，措辞风格、格式习惯、判断方式都不同。上下文里存的全是前一个模型的写法，接手模型要花注意力去推断这些内容的言外之意，上个模型说这句话时认定过什么、否决过什么。从头就用同一个模型没有这笔开销，历史是自己写的，不用解释。**上下文越长，接手模型要花越多注意力去读懂前人的话**，风格噪音随之放大。

上一篇《[上下文决定智能体的上限](./context-matters.md)》讲上下文越充足，智能体表现越好。本文要给它补一个边界条件：上下文必须和读它的模型兼容。自己写的历史是资产，另一个模型写的历史在长上下文下会变成噪音。fork 场景把这个边界问题放到最大：**fork 越多、背景越长，子智能体读起来反而越差，多给的背景只是噪音**。

### "继承父模型"也会被打破

pi-subagents 默认让子智能体继承父模型，不需要显式配置。看源码里的`resolveDefaultModel`就清楚：优先级从高到低是 explicit option、config.model、parent model，最后一项取的是委派时刻主智能体正在用的模型。

问题出在"委派时刻"上。主智能体在会话中途切换过模型的话，委派时 fork 拿到的历史就是混合风格的：切换前旧模型写的部分，加上切换后新模型写的部分。**旧模型写的历史会一直留在上下文里**，新模型的输出只能让它占比变小，无法替换它本身。**压缩是唯一真正的净化机制**：切换后触发压缩，摘要由新模型写，旧模型的历史才真正退出上下文。压缩不一定发生，没有压缩时旧模型的风格噪音只能被稀释，清除不了。

于是出现一个最差的组合：切换模型后不久就委派。fork 拿到的是新旧两段风格混合的历史，跨模型读取损耗正好落在最大处。不巧的是，这在我自己的使用里是常态，切换模型通常是因为当前模型不够用，切完继续干活，干着干着就要委派拆任务。**切换后不久就委派，是 fork 性价比最差的时刻**。

## 结果与教训

把前面几节的账放在一起，fork 的安全区需要四个条件同时成立：主智能体从未在会话中途切换模型、子智能体不显式配置模型走继承、不在乎缓存成本、上下文还没长到读取损耗盖过收益的程度。**fork 的安全区需要四个条件同时成立**。

这四个条件在我的系统里几乎不可能同时成立。我的 [subagent-isolation](https://github.com/Wolido/subagent-isolation) 体系（包括 [async-subagent-isolation](https://github.com/Wolido/async-subagent-isolation)）从设计上就把多模型分工当作前提：主智能体和子智能体各配各的模型，子智能体按任务类型配专门的模型。主-子异模型是常态，fork 直接被排除。

在我的架构前提下，**把背景写进委派任务文本，是多数场景下更经济的选择**。task 文本短，几百 token 的量级，缓存影响可以忽略。写 task 的过程就是在为另一个模型写提示词，详略和格式天然适配接收方。给多少背景由主智能体自己判断，按任务调整。写全量背景确实费脑，这是这条路的主要成本。

fork 也有自己的适用位置，我判断它的价值在背景复杂度这一侧。任务依赖的决策历史长到主智能体几句话概括不了时，把背景转述成任务文本的成本会超过 fork 本身的损耗，fork 的无损和零转述优势在这个区间才成立。**fork 是背景复杂到转述成本过高时的逃生门**。判断该不该 fork，我一般看三件事。背景复杂到主智能体几句话讲不清，才值得 fork。主智能体和子智能体是同模型或同族模型时，跨模型读取损耗小得多，异模型时这笔损耗就在最大处。主智能体没切换过模型，或者切换后已经充分对话、压缩过，历史里旧模型的痕迹已经被稀释或替换，fork 的内容要好读得多。

task 路线的费脑成本有现成的缓解办法：让当前模型先写一份短的交接摘要，再作为任务背景附上。上一篇讲的交接清单是跨会话的做法，这里要的是跨模型的交接：**短摘要交接是比全量继承更划算的做法**。

最后对照一下 pi-subagents 的处境。同一个功能在两个架构里的代价不同：pi-subagents 的典型用法是同模型继承，跨模型读取损耗在它那里天然小；我的系统从设计上鼓励多模型分工，异模型是常态，在我的架构下 fork 一进来就同时撞上缓存和读取质量两堵墙。功能本身没有对错，**同一功能的代价取决于架构前提**。
