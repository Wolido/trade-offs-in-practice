# 把失败当作接口来设计：harness 的失败语义

harness 在智能体语境下**至少有三层意思**。第一层是评测脚手架，负责把任务、题目和评分规则串成测试环境。第二层是能力层，给模型接上工具，把工具调用翻译成系统指令。第三层是可靠性层，约束行为边界、处理错误。关于 harness 的讨论大多落在前两层，第三层很少有人正经展开。第三层问的是另一个问题：**模型做错的时候，系统呈现出什么样子**。这个问题没法靠模型自觉，答案在 harness 的设计里。我在这层上最重要的实践习惯是：**把每个失败点都当作一个需要设计的接口**。

我这边有个现成的观察窗口。我自己开发的 [async-subagent-isolation](https://github.com/Wolido/async-subagent-isolation) 扩展，是 [subagent-isolation](https://github.com/Wolido/subagent-isolation) 的异步版，跑在 [pi](https://github.com/earendil-works/pi-coding-agent) 上。机制我在上一篇[《主智能体的能力约束》](./capability-constraint.md)里写过：主智能体被硬剥夺 write、edit、bash，只剩 read、grep、find、ls 四个只读工具，加一个委派子智能体的工具；子智能体跑在独立的 pi 进程里，异步派出，结果以 `[subagent-result]`系统通知回流。上一篇和[《上下文里的"行动残渣"》](./context-residue.md)、[《Skill 的作用域隔离》](./skill-isolation.md)分别处理越权、上下文污染和 skill 干扰三类问题，讲的是 harness 防什么；本文讲另一面：出错的时候，系统呈现出什么样子，模型从哪里恢复。

先说一个无害但很典型的失败。有段时间我把主智能体换成性能差一些的模型，立刻出现一种口误：它直接调用一个叫 `writer`的工具，而实际工具列表里只有一个叫 `subagent`的工具，`writer`只是`subagent`的`agent`参数。我猜原因在这里：子智能体清单注入系统提示词之后，agent 名称的显著性压过了工具 schema 的约束力，模型记住了角色名，没有去查工具定义。

这个失败是很好的观察样本。调用一个不存在的工具，harness 直接报错，没有任何副作用，错误信息本身就把纠正做完了，模型下一轮改对重发，代价只有一轮对话。**委派入口、错误模式、恢复路径，都收敛成了唯一形态**。这三点是设计出来的：委派收敛成单入口，没有旁路可绕。错误信息是写给模型看的下一步操作说明，内容只有两件事：发生了什么，接下来怎么走。

真正用力的是 sessionId 的复用防护。派发回执会鼓励模型复用 sessionId 继续同一任务，能省掉重新交代上下文的开销；但**带着在途任务的 sessionId 再次派发，会被结构性拒绝**，错误消息直接给出三条出路：等通知、取消，或者省略 sessionId 另开新任务。

不放行是有据可查的，源码注释把后果写得很直白。一旦放行，旧进程还在跑但完成回调丢了，会变成孤儿进程，跑完也没人接收结果。cancel 找不到旧进程，取消直接失效。两个进程同时写同一个 session 目录，还会互相污染，目录最后是什么状态都说不清。三个故障随便摊上一个，都比一次拒绝更贵。

围绕这个入口还有一整条防护链：sessionId 必须是特定格式的小写 UUID v7，编造的 id 直接拒绝；异步模式下格式校验和复用拒绝都前置，错误在派发回执之前返回，不让"假成功"进入异步流程；完成记录去重，同一 sessionId 复用多轮时最新一次完成获胜。这些规则大部分时间静默，但每一条都对应一类真实事故，把失败挡在入口之外，比等它进入异步流程深处再处理便宜得多。路径穿越检查不在这条链上，它在创建 session 目录时兜底：异步路径下回执已经先返回，路径穿越失败以 `[subagent-result]`失败通知的形式事后到达，同样零副作用。

## 失败和成功必须长得不一样

比"错误信息怎么写"更前置的问题是返回形态。**失败和成功的返回形态必须可区分**。

模型是模式匹配器，它消费工具返回值的方式，是看它读起来像不像成功。如果某个操作的错误返回，和另一个场景下的成功返回在文本形态上相似，模型就可能把失败当成成功继续往下走。这种混淆失败比普通失败严重得多：普通失败是"我知道没成，重试"；混淆失败是"我以为成了"，后续所有动作都建立在假前提上，越往后越难发现。

这个扩展里，这类设计是成系统的。派发回执只有孤零零一句，声明 `Dispatched`并给出 `taskId`，真正的结果以 `[subagent-result]`通知信封送达，两者形态完全不同，工具描述里还反复强调，回执不等于结果。如果回执长得像一段结果摘要，这个形态分离就没有意义。通知信封带显式结构化的状态字段，取值固定四种：succeeded、failed、timed out、cancelled，模型不需要从正文语气里猜成败。前面的校验前置，也是在防混淆：非法 sessionId 如果也先返回一个正常样式的派发回执、后台再失败，错误就和成功长得一样了。幻觉工具名那条也一样，报错是明确的"工具不存在"，和成功派发的回执没有相似之处。

反面反模式在别的工具里常见。我见过一些 bash 封装，把 stderr、非零退出码和正常输出混在一大段文本里原样返回，模型得自己从文本里判断成败；还有把空结果返回成空字符串的，"操作成功但没数据"和"操作失败"在形态上分不出来。这两种形状等于把判断责任抛回给了模型。

异步通知一侧也有消化纪律。`[subagent-result]`信封自带固定触发行，提醒模型这是一条任务完成通知，先锚定主线任务，再消化结果。信封里带一份在途任务快照，并显式声明快照可能滞后，和模型自己的派发记录冲突时以派发记录为准。取消走两步确认，用户主动取消的任务不会自动重试。

## 能数得过来的错误，才值得设计

把前面这些机制放在一起看，会发现它们有一个共同的前提。**防护能做密，因为错误空间小到值得做密**。

这里有两条约束路径在合谋：收窄能力面管的是错误的**数量**，把错误空间缩到可枚举；另一条路径要给每种错误配好明确的错误信息和恢复路径，让每一个可枚举的错误都被预先设计，这管的是错误的**质量**。

主智能体手里只有五个工具：四个只读工具加一个委派入口。它能犯的错误掰着指头数得出来：幻觉工具名、委派参数写错、sessionId 格式错、复用带在途任务的 sessionId、委派层次超限。每一种错误都能预先识别，配好错误信息和恢复路径。所有防护都靠结构实现，提示词里的恳求挡不住结构性坏状态。对比另一种情形：如果主智能体手里有几十个工具，调用组合空间是指数级的，错误模式不可枚举，设计者没法逐一预设计，只能依赖模型不犯错。

这套防护能做得这么密，会遇到一个直觉反驳：只给五个工具，复杂任务怎么办。我的回答是，**复杂度没有消失，它从模型的运行时行为转移到了静态结构里**。

留在一大堆工具里，复杂度表现为模型当场挑选、当场组合，每一步都靠临场判断，每次运行都是一次新的即兴发挥，结果不可预测，事后也难复盘。放进结构里，复杂度表现为层级化的子智能体分工：主智能体只拆分任务，子智能体各自握着有限的工具和专注域，复杂任务靠拆分和组合完成。结构是静态的，能完整写出来，也能针对性地评审和测试。把复杂度消化在结构里，用结构换行为，软件工程早就在做：微服务拆分之后，单体内部隐性的调用复杂度变成了显式的服务拓扑；类型系统也干过类似的活，把运行时的约定检查提前到了编译期。上一篇[《主智能体的能力约束》](./capability-constraint.md)讲的硬剥夺，就是这条路径的起点：把执行能力从行为空间里拿走，逼着复杂度流进结构。

这套思路往前推一步，就是分布式系统里那个熟悉的纪律：先定义失败行为，再谈正常流程，TCP 在"线路必然丢包"的前提下设计重传。**智能体 harness 给同一个纪律换了一个前提：调用方是一个不可靠的概率模型**。

## 零副作用是其他原则的地基

把每个失败点都设计一番，前提是每一个失败都不贵。

这个扩展的失败路径都是零副作用的：幻觉工具名只返回一条错误文本；非法 sessionId 在派发之前就被拦下，后台进程根本没有被创建；复用带在途任务的 sessionId 被拒绝，旧进程、新任务、session 目录三者原样不动。**判据只有一条：失败发生的那一刻，系统状态和失败之前完全一样**。

零副作用往下渗，前面几条结论都靠它撑着。错误可枚举有价值，先决条件是每个错误都不贵：认出错误就够了，不需要额外善后。恢复路径写成简单的"改对重发"就行，副作用为零意味着没有残局可清理，"先清理残局再重试"这种复杂流程根本不存在。"让模型放手去试"这个心态同样建立在这块地基上：模型是会犯错的组件，系统设计的问题就变成每次犯错的成本是多少，是零，还是一个需要人来收拾的现场。零副作用把"模型犯错"从事故降格成了噪音。

这个方向很少被展开讲，我的观察里原因有四个。

最先该说的原因在话语权。模型厂商的利益在"模型足够聪明、不需要枷锁"的叙事里，**讨论可靠性 harness 等于承认模型会犯错，需要外部结构兜底**。应用开发者大多还在"能不能跑通"的阶段，可靠性的病要重度使用才发作，而且 agent 事故大多被笼统归成"模型还不行"，很少有人意识到那是 harness 缺失。

第二个原因是它没有展示性。**可靠性 harness 的成果是"什么都没发生"**。没发生的事 demo 看不出来、benchmark 测不出来，预防性工作不如救火显眼。

再一个是立场问题。设计这种 harness 的前提，是把模型当成会出错的组件来做容错工程，很多人觉得这和 AI-native 叙事冲突。但软件工程的历史是另一回事，每个可靠性实践几乎都在组件相当可靠之后才成熟，**harness 的价值随系统变复杂而升值**。

最后是方法论缺席。现有实践是点状的：权限弹窗、human-in-the-loop、各种 trust 机制各有各的做法，缺的是把整套抽象成设计原则来讲。

这套实践能抽象出来的原则是有层次的：失败零副作用是地基；有了这个地基，错误空间可枚举才成为值得追求的前提；每个错误一旦能被枚举，形态就必须明确，恢复路径也必须自描述。它们有一个共同性质：跨模型稳定。**模型每半年换一代，追着模型写的提示词半年过时，harness 层的经验是积累的**。

这也是我写这篇文章的原因。下一个模型可能还会犯 `writer`那种口误，只要 harness 把失败设计好了，**犯错的代价只是一轮对话，因为副作用为零**。
