# Skill 的作用域隔离：让每个智能体只看见自己需要的 skill

## 观察

搭建多智能体系统时，你会陆续给智能体写一些 skill 文档，告诉它某个具体任务该怎么做。一开始只有两三个，后来想到新的场景就加一个，再后来发现某个子智能体需要特定领域知识，又加一个。skill 池就这样长起来的。

如果所有智能体共享同一个 skill 池，增长会带来一个结构性问题：**每个智能体都能看到全部 skill，skill 越攒越多，选择越来越难**。三个 skill 的时候扫一眼就定了；三十个的时候，光是读完所有描述就要占不少 token，读完之后的判断也更可能出错。skill 池增长带来的问题是：候选集膨胀后，智能体在"该用哪个"这件事上的决策负担显著变重了。

skill 池膨胀的后果，上一篇（[上下文里的"行动残渣"](./context-residue.md)）已经触及了一个侧面：skill 描述也是上下文内容，它们占据 token，参与每一轮推理。但本文关心的不是 token 占用，而是另一个更隐蔽的问题：候选集大小和选择准确率之间的关系。skill 描述不仅是上下文负担，它还是一种引诱。

## 问题

关于候选集膨胀对选择准确率的影响，学术界有一些直接相关的发现。

一篇题为 Less is More 的研究（[arXiv:2411.15399](https://arxiv.org/abs/2411.15399)）给出了一个干净的结论：**工具数量增多直接拉低 function calling 的任务完成率**。候选集越大，模型在选出正确工具这件事上表现越差。另一项关于注意力溢出的研究（[arXiv:2407.13481](https://arxiv.org/abs/2407.13481)）则从机制层面给出了观察：候选项到达约 100 个时，注意力开始明显模糊（该阈值在缺失项推荐场景下测得，基于 2024 年中旗舰模型）。IBM Research 的 ToolRM（[arXiv:2509.11963](https://arxiv.org/abs/2509.11963)）在 Best-of-N 采样下多个基准上最高提升了约 25%。

这些研究的共同指向是：候选集大小和选择准确率之间存在反向关系。这个判断有独立研究的支撑。

但这件事在我的系统里还有一个更微妙的维度。

skill 的描述是激活机制。它的设计初衷很明确：智能体读到描述，判断"这个 skill 是不是我现在该用的"。描述写得越精准，正确的智能体就越容易在合适的时机激活它。

**对不需要这个 skill 的智能体来说，描述写得越好，副作用越大**。

一个给 writer 用的写作风格检查 skill，如果描述写的是"检查段落节奏、句子长度分布、主动被动语态比例"，writer 读了觉得顺手，coder 读了也觉得"这好像能帮我校验代码注释"，主智能体读了更可能想"我可以先检查一遍再委派给 writer"。描述是写给特定使用者的，但共享 skill 池里所有人都能看到它。对不需要它的人，精准的描述就是诱饵：越精准越吸引人，越吸引人越容易被误用。

这就是共享 skill 池的核心悖论：**把描述写好，在共享池里是负优化**。每个 skill 的描述是针对特定角色的，对其他角色是噪音甚至毒药。skill 越多，毒药越多。

## 判断

### 1. 静态角色分区

解法很直接：**按角色预切 skill 空间，互相不可见**。

每个子智能体只加载自己需要的 skill。coder 看到的是调试、代码审查类 skill；writer 看到的是写作、风格类 skill；reviewer 看到的是验证、测试类 skill。一个角色看不到另一个角色的 skill 列表，更读不到它们的描述。

它和运行时动态筛选不同：skill 在定义阶段就绑定到角色上，运行时不变。

这个做法把**skill 选择准确率从运行时的概率问题变成了结构上的确定性**。智能体不会选错 skill，因为对它来说，不该选的 skill 根本不存在。候选集从一个需要搜索的空间变成了一个预设的、有界的列表。

在我当前的配置里：主智能体加载几个工作流用的 skill（处理 issue、写作、决策分析这类）；coder 加载 systematic-debugging 等调试类 skill；writer 加载写作类 skill；reviewer 无 skill。每个智能体只看见自己需要的，其余一概不可见。

### 2. 与动态检索的对比

学术界和工业界对"候选集太大"这个问题的常见解法是动态检索：在运行时根据任务内容检索相关 skill 描述，动态注入上下文。文献中常称为 RAG-over-tools。

两种做法攻击的是同一个变量：候选集大小。路径不同。

**静态分区是确定性的、零检索延迟、零检索错误**。没有"该检索到但漏了"的问题，也不存在检索步骤本身消耗的 token 和延时。代价是需要人事先把 skill 划分清楚：哪个 skill 归哪个角色。**这是用人的工作换模型的确定性**。对我而言，这个交易值得：人的划分做一次、审计一次；检索的决策每次都要做，而且可能静默失败。

我目前没有做过静态分区和动态检索的对照实验，这里只能谈谈我的使用场景：静态分区的确定性让我更省心。它的行为是可预测的，出问题时也容易定位：要么是 skill 分错了角色（人犯的错，改一次就好），要么是角色职责写得不清楚（改提示词）。没有"这次检索为什么漏了那个 skill"这类需要反复排查的问题。

### 3. 主智能体的 skill：少而专

主智能体的情况值得单独讨论。

[上一篇](./capability-constraint.md)讨论过，主智能体被后训练成"亲自解决问题的智能体"，拿到任务就想自己上手。当它挂着大量 skill 时，这个倾向会被放大。规划过程中它看到各种 skill 描述：这个能"分析代码质量"、那个能"检查文档一致性"。**大量 skill 会让主智能体忍不住亲自介入**。它会想：这个 skill 好像能直接帮我做这件事，不如我先试试。于是亲自读、亲自用，上下文里塞满执行细节，规划能力被稀释。**skill 池越大越助长它**。

这与上一篇描述的"上下文越满越固执"是同一种退化模式，只是触发路径不同：那里是执行痕迹堆积，这里是 skill 描述引诱。

所以**主智能体的 skill 只保留自己工作流需要的几个**。我目前只给它挂了几个处理特定问题的流程化方案类 skill，数量很少。所有执行类的领域知识（怎么写代码、怎么润色文字、怎么跑测试）全部分配给对应的子智能体。主智能体不需要知道这些，知道了反而有害。

这背后有一个更一般的判断。**对智能体而言，必然要加载的知识就不该放在 skill 里**。角色定位、职责边界、硬约束这类常驻知识，直接写进系统提示词就行，比如 agent 定义文件或 master.md。skill 池只放按需加载的内容。

除了让 skill 池更小，这样做还有实际性能收益。常驻知识放进系统提示词，省掉了 skill 加载的整套步骤：智能体不用先判断"该不该用这个 skill"，省一次推理；也不用 read skill 文件，省至少一次工具调用。此外，系统提示词是常驻的，前缀缓存可以命中，不会重复计费；skill 是临时读取的，每次会话都要重新加载。

主智能体的情况正是如此。它的角色定位和硬约束（不能写、不能改、必须委派）都在 master.md 里，skill 只挂几个工作流按需用的。它的 skill 少，是因为常驻知识已经在系统提示词里了，skill 池自然就轻。

### 4. 封装视角：接口即契约

把 skill 按角色封装之后，**主智能体对子智能体的全部认知就是名字加一句话职责描述**。这条描述就是公开接口。子智能体的系统提示词、工具白名单、skill 列表，全是私有实现。

有人会担心这构成盲委派：主智能体不知道子智能体具体能做什么、不能做什么，只能在错误中学习路由。但我的体验不是这样。关键是接口描述写得是否清楚。主智能体的系统提示词里，我把每个子智能体做什么写明白了——"coder 负责写/改生产代码、修 bug、重构""writer 负责写/润色文档、文案、commit message""reviewer 负责审查变更、检查 bug 和风险"。**描述质量决定路由质量**。实际用下来，这套描述没有出过能力错配的问题。路由准确率的瓶颈是描述写得好不好，跟主智能体知不知道子智能体的内部 skill 列表关系不大。

这个感受来自我在几个项目里的实际使用。把接口写清楚，路由就准。

## 结果与教训

skill 隔离之后，最直接的效果是：skill 选择错误这一类问题基本消失了。选错的物理前提被移除了：看不到就不会选错，跟模型聪明不聪明无关。

更大的收获在架构层面。**横向隔离与纵向隔离是正交的两条轴，合起来构成完整的隔离架构**。纵向隔离（[主智能体的能力约束](./capability-constraint.md)）控制智能体能做什么——主智能体不能写、不能改、不能执行。横向隔离（本文）控制智能体能看见什么：每个角色只看见自己的 skill，其余不可见。两条轴各自攻击不同的问题，互不替代。

事后看，skill 隔离这个方向有一个判断是对的：不要指望模型在大量选项中总能做出正确选择。把选项收窄，把不该选的选项藏起来，比任何提示词优化都更可靠。**结构性约束比行为引导更值得信赖**。这和上一篇的结论是同一种逻辑，只是作用在不同维度上。
