# 为什么主流框架不做硬隔离

## 观察

前三篇文章讨论了一个层层递进的隔离架构：纵向剥夺主智能体的执行权限（[主智能体的能力约束](./capability-constraint.md)），横向按角色切分 skill 空间（[Skill 的作用域隔离](./skill-isolation.md)），中间还有一层上下文污染的治理（[上下文里的"行动残渣"](./context-residue.md)）。每篇文章的结论都指向同一个方向：**结构性约束比行为引导更可靠**，把不该做的事从物理上禁止，比反复叮嘱"别做"有效得多。

这自然会引出一个困惑：如果隔离这么好，为什么 Codex、Claude Code 这些主流框架不这么做？

我最初也在这个问题上卡了很久。困惑不等于答案。"它们没做"和"它们错了"之间隔着整个商业产品决策的逻辑。本文想做的就是把这段逻辑展开。

## 问题

把"为什么不做"转成可分析的问题，需要先问：**商业框架的目标函数是什么？**

一个面向付费用户的商业产品，和一套面向自身工作流的个人系统，优化的东西完全不同。商业产品的核心约束大致可以归纳为：**绝大多数用户的任务在几十步以内就能完成，而每多花一个 token 都是成本**。这个约束集合里包括中位数任务长度、按量计费的 API 模型、需要兜底的容错机制，它们共同构成了商业框架做所有架构决策的边界条件。

在这个目标函数下，硬隔离的收益-成本曲线是什么样的？我判断，**主流框架想到了硬隔离，但最终选了曲线上更软的点**。下面从四个维度展开这个判断。

## 判断

### 优化中位数而非长尾

商业产品面向的是大多数用户的中短任务。据公开信息判断，Codex 和 Claude Code 的典型使用场景是单次对话几十步以内的开发任务：改一个文件、加一个功能、修一个 bug。在这些场景里，硬隔离的委派开销比直接执行多绕了一圈：主智能体描述任务、子智能体执行、主智能体验收。而隔离带来的上下文整洁度提升在短任务上几乎体现不出来。

**硬隔离的收益随任务长度非线性增长**。我的体验是，任务超过约 50 步之后，上下文的累积污染才开始显著拖累推理质量；超过 100 步后隔离的收益变得明显。但商业产品的绝大多数用户根本走不到这个长度。**为中位数优化意味着不为长尾付出架构复杂度**，这个选择在商业上完全合理。

商业框架内部很可能评估过硬隔离方案，但这个评估是在"为谁优化"这个更根本的选择之下的。为长尾优化和为中位数优化，走的是两条不同的架构路径。

### 进程隔离杀伤缓存经济性

这是一个更硬的约束。多进程架构下，每个子智能体跑在独立进程里，每次委派时子智能体的上下文从零开始构建。而单进程架构里，主智能体直接执行时整个会话共享提示词前缀，API 提供商的提示词缓存让后续工具调用的输入 token 几乎免费。

**每委派一个独立进程，前缀缓存就被打断一次，token 成本成倍增加**。对按 API 用量计费的商业产品来说，这是直接的成本项。Claude Code 的 Task tool 恰好提供了一个观察窗口：**它做了子智能体，但把隔离程度做成可选的**，同进程内启动，缓存可以部分复用，何时委派的决定权留给模型和用户。它考虑过子智能体，最终在缓存效率和控制粒度之间取了折中。

软子智能体（同进程）能部分保住缓存复用，硬进程隔离保不住。这个差异在单次对话里可能只是几美分，但乘以上万用户的日活，就是一条不可忽略的成本线。

### 信息瓶颈在中短任务是净损失

委派天然带来信息损耗。主智能体看子智能体的输出摘要，不读完整执行过程，这本身就是一次有损压缩。**亲手改代码时对代码库的感知是一手的，透过子智能体的摘要去理解是二手的**。

短任务里，这个损耗比亲自执行带来的上下文膨胀更贵。改一个函数、修一行配置，自己做一眼看清；委派出去，描述任务、等待返回、阅读理解摘要，链条更长、出错点更多。隔离的收益在任务链足够长时才超过这个损耗。**在中短任务区间，信息瓶颈是净损失，不是净收益**。

据可观察的行为推测，商业框架的设计者对此有清醒的判断：与其在短任务上承受委派的信息折损，不如让主智能体直接执行，用定期压缩控制上下文长度。这是一个**用更软的代价换取更低的短任务损耗**的选择。

### 顶层保留容错路径

即使做了工具剥夺，主智能体仍然可以通过 bash 间接操作文件系统。这个保留不是设计漏洞，**它是最后的容错路径**。

子智能体可能遇到各种无法处理的情况：某个工具在子智能体的环境里出 bug、委派返回的格式不符合预期、子智能体对特定领域的判断持续出错。在这些场景下，主智能体亲自介入的能力就是安全阀。商业产品不能接受"系统在某个边界情况下完全无法自愈"，**把执行能力留在顶层，即使这意味着上下文会被污染，也是一项合理的保险**。

这和硬隔离架构的取舍不同。硬隔离用顶层执行能力的完全剥夺换取上下文的彻底整洁，代价是失去了最直接的容错手段。我的系统里通过 reviewer 子智能体来弥补这个缺口，但这引入了额外的复杂度和延迟。商业框架选择保留顶层的灵活度，在这个维度上是成本更低的选择。

## 结果与教训

回过头看，**硬隔离不是普适最优，是某个区间的最优**。分界线大致由三个变量决定：任务长度、主智能体与子智能体的耦合度、对上下文污染的容忍程度。

**当任务链很长、耦合度低、对污染敏感时，硬隔离的收益超过成本**。具体来说，百步以上的任务链、子智能体可独立完成子任务、推理质量在长上下文下显著下降，这三个条件同时满足时，硬隔离是值得的。而当任务短、耦合紧、验证需求高时，软隔离或直接执行是更高效的选择。

这也可以换一个角度说：主流框架用了软约定、按需下放探索和压缩，以较低的架构成本拿到了大部分隔离收益，同时保留了兜底和可观测性。**这不是"好方案为什么没人用"，而是一个 trade-off 的两端，商业产品选了另一端**，在那个端点，它们的约束条件下收益最大。

对我自己的系统而言，这个分析也让我更清楚硬隔离的适用边界。硬隔离只在任务复杂度越过某个阈值之后才值得。知道什么时候不该用，和知道什么时候该用，是同一种判断的两个侧面。
