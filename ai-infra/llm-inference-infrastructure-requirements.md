# 大模型推理服务基础设施要求

> 目标：明确一个大模型从权重文件变为可用 API 服务时，对 GPU、服务器资源、软件依赖、模型适配、网络与运行环境的要求，并形成部署前检查和上线验收依据。

一个可用的大模型 API 服务，需要模型架构、权重加载、状态管理、解码流程、GPU 算子、推理引擎和服务器软硬件环境共同配合。


---

## 一、明确推理服务的基础设施边界

### 1.1 三种不同的“能运行”

大模型部署中，“能运行”至少包含三个不同层次。

**能读取权重**：模型仓库文件完整，框架能够识别 `safetensors` 等权重格式、分片索引和模型配置。这一层只说明模型文件可以被读取，不代表模型已经能够执行。

**能正确推理**：推理引擎已经具备对应的模型实现，能够完成权重映射、Tokenizer 与 Chat Template 处理、前向计算、状态更新和解码。输出不仅要“有文字”，还要符合模型的预期行为。

**能持续服务**：在目标上下文长度、并发数和输出长度下，服务能够稳定处理真实请求。此时还要满足显存、主机资源、多卡通信、缓存回收、API 超时和流式输出等要求。


### 1.2 推理服务依赖的完整技术栈

一个典型的推理服务可以抽象为以下层级：

```text
API 服务与输入处理
OpenAI 兼容接口、Tokenizer、Chat Template、多模态 Processor
        ↓
调度、解码与状态管理
请求排队、连续批处理、Prefill/Decode、KV Cache、Mamba/GDN 状态
        ↓
推理引擎与模型实现
模型注册、权重映射、并行切分、执行器
        ↓
GPU 算子与多卡通信
Attention、GEMM、MoE、量化、Sampling、NCCL
        ↓
驱动、CUDA 与服务器硬件
GPU、显存、CPU、内存、磁盘、互联拓扑
```

任何一个层级不满足要求，都可能使服务无法启动或无法正确使用。

例如，模型架构未注册属于模型实现问题，`nvcc` 缺失属于编译工具链问题，而没有兼容内核则可能与 GPU 架构、数据类型或算子有关。

### 1.3 部署前必须明确的四类输入

部署前应先把以下信息收集完整，再讨论启动参数和资源规格。

| 类别 | 必须确认的信息 |
|---|---|
| 模型侧 | 准确名称和版本、`architectures`、`model_type`、权重精度、量化格式、原生上下文长度、解码方式、文本或多模态能力、是否包含自定义代码 |
| 引擎侧 | vLLM/SGLang 版本、模型注册情况、量化解码支持、多模态支持、TP/PP/EP 支持、是否依赖特定分支或补丁 |
| 硬件侧 | GPU 型号、数量、显存、计算能力、CPU、主机内存、NUMA、磁盘、多卡与多机互联 |
| 软件侧 | GPU 驱动、Python、PyTorch 及其 CUDA 版本、CUDA Toolkit、内核库、NCCL、Tokenizer/Processor 依赖 |

注意：模型仓库中的 `config.json` 只是结构声明，`modeling_*.py` 通常是模型作者提供的参考实现，它们不会自动转化为 vLLM/SGLang 的生产级实现。

即使 Transformers 能运行，也不能据此推断目标推理引擎一定支持。

## 二、GPU 与服务器硬件要求

### 2.1 GPU 型号与计算能力

GPU 检查不能停留在“显卡数量”和“显存大小”，至少还应确认以下项目：

- GPU 的准确型号和 Compute Capability。
- 单卡显存、卡间可用显存是否一致。
- 模型和推理引擎需要的 BF16、FP16、FP8、INT4 等数据类型是否受支持。
- Attention、MoE、量化、采样以及 Mamba/GDN 等专用内核是否支持当前 GPU 架构。
- 当前内核是否还对 dtype、shape、量化分组方式或模型结构有额外限制。

同一模型在不同 GPU 上的表现差异，可能并不来自显存，而来自内核支持范围。如果某个专用内核只支持特定架构，那么安装其他版本的 CUDA Toolkit 也不会改变 GPU 的硬件计算能力。

因此，GPU 应该具备两个条件：**资源是否足够，以及硬件能力是否匹配。**

### 2.2 多卡互联与并行条件

多卡部署需要区分“机器里有多张 GPU”和“多张 GPU 能组成一个满足要求的推理实例”。

张量并行（TP）需要在模型计算过程中频繁交换结果，对机内互联带宽和延迟敏感，部署前应检查：

- GPU 之间通过 PCIe 还是 NVLink 等方式互联。
- 实际拓扑是否与计划的 TP、PP 切分方式匹配。
- 多机场景是否具备满足要求的网络与 NCCL 通信条件。
- 是否出现通信库回退到低速传输路径的告警。
- 多卡显存是否均衡，是否存在单卡先成为容量瓶颈的情况。

如果模型必须跨节点运行，还需要把节点间网络作为推理实例的一部分进行验收，而不能只检查 API 网络是否连通。

### 2.3 CPU、主机内存与 NUMA

CPU 和主机内存虽然不直接保存全部模型计算，却会影响模型加载和在线服务的稳定性。

CPU 主要承担 Tokenizer、请求调度、Python 运行时、部分数据搬运以及图片和视频预处理。多模态服务尤其需要关注解码和预处理造成的主机侧开销。

主机内存需要容纳权重读取和转换过程中的临时数据、运行时缓存、输入输出数据以及多模态预处理结果。不能仅以“模型权重大小小于 GPU 显存”为依据规划主机内存。

在多 NUMA 节点服务器上，还应检查 GPU、CPU 和内存的拓扑关系。若计算进程、内存和 GPU 跨 NUMA 节点分布，可能增加数据访问和通信开销。

部署前应先确认拓扑，再决定是否需要绑定，而不是直接套用其他服务器的绑定参数。

### 2.4 磁盘与本地存储

磁盘规划应覆盖完整运行周期，而不是只计算一次模型下载所需的空间。

| 存储项目 | 需要预留的内容 | 空间不足的典型影响 |
|---|---|---|
| 模型文件 | 权重分片、配置、Tokenizer、Processor | 下载不完整、权重加载失败 |
| 模型缓存 | 下载缓存、多个模型或版本 | 无法更新模型、重复下载 |
| 编译缓存 | CUDA/Triton JIT 产物、Autotune 缓存 | 编译失败、重启后重复编译 |
| 容器与依赖 | 镜像、Python 包、系统依赖 | 部署或回滚时无法恢复环境 |

生产环境还应考虑模型升级期间新旧版本短暂共存的空间，避免磁盘只够保存当前一个版本。

## 三、资源容量规划要求

### 3.1 显存需求不能只计算模型权重

模型权重可以用“参数量 × 每参数字节数”做初步估算，但这只是显存需求的一部分。完整预算应按以下框架评估：

```text
总显存需求 ≈ 模型权重
           + KV Cache
           + Mamba/GDN 等状态
           + 激活与临时缓冲区
           + CUDA Graph
           + 多卡通信与系统预留
```

其中，权重主要是相对固定的占用，缓存和状态则随请求长度、并发数及运行方式变化。CUDA Graph、通信缓冲区和临时工作区也需要在权重加载后保留空间。

因此，“权重刚好放得下”通常只说明可以尝试加载模型，不代表实例能够接收真实请求。

### 3.2 KV Cache、状态空间与并发容量

对于常见 Transformer 模型，可以用下式理解 KV Cache 的主要影响因素：

```text
KV Cache ≈ 2 × 层数 × KV 头数 × 每头维度
           × 已缓存 Token 总数 × 每元素字节数
```

这里的“已缓存 Token 总数”与所有活跃请求的上下文、已生成内容和缓存保留策略有关。

上下文越长、并发越高，所需的缓存空间通常越大。采用 GQA、MQA 或不同缓存精度时，应使用模型实际参数计算，不能直接按普通多头注意力估算。

混合架构还可能包含线性注意力或状态空间层。除了 KV Cache，这类模型可能需要保存：

- Recurrent State；
- Convolution State；
- 投机或其他解码路径的中间状态；
- 前缀复用对应的历史状态。

因此，混合模型不能只按传统 KV Cache 公式估算显存，还要确认推理引擎如何分配状态池、每个请求占用多少状态槽位，以及状态槽位是否会先限制最大并发。

前缀缓存能够复用相同系统提示词或多轮对话前缀，减少重复 Prefill，但复用本身也需要缓存空间。它改变的是计算量和缓存占用方式，并不意味着可以忽略容量预算。

### 3.3 容易低估的容量项目

**MoE 权重**：单步计算只激活部分专家，不代表只需要保存被激活专家的权重。除非实现明确采用其他存储和加载机制，否则仍应为完整模型权重规划空间。

**量化后的运行时占用**：权重量化主要减少权重存储和部分带宽压力，不会同比例减少 KV Cache、激活、通信缓冲区和 CUDA Graph 占用。

**上下文与输出的组合**：最大输入长度和最大输出长度会共同影响单个请求的资源占用。少量长生成请求也可能长期占用缓存，不能只用平均请求长度评估容量。

**首次启动开销**：JIT 编译、Autotune 和 CUDA Graph 捕获可能引入额外的主机或设备资源需求。启动阶段的资源峰值也需要关注。

### 3.4 区分最低启动标准与生产运行标准

容量规划应明确区分两套标准：

| 标准 | 验证目标 | 不能代表什么 |
|---|---|---|
| 最低启动标准 | 小上下文、低并发下完成模型加载和正确生成 | 不能代表目标生产负载可运行 |
| 生产运行标准 | 在目标输入长度、输出长度和并发分布下持续稳定运行 | 不能只通过一次短请求验收 |

生产验收应使用接近真实业务的长度分布和并发模型，观察显存、缓存占用、请求中止后的资源回收以及长时间运行是否稳定。

## 四、软件栈与模型适配要求

### 4.1 驱动、CUDA 与编译工具链

GPU 驱动、CUDA Runtime、CUDA Toolkit 和推理引擎承担不同职责，不能把它们视为同一个组件。

| 组件 | 基础设施要求 | 缺失或不匹配的典型表现 |
|---|---|---|
| GPU 驱动 | 操作系统能够正常识别和访问 GPU | GPU 不可见、CUDA 初始化失败 |
| CUDA Runtime | 与 PyTorch、推理引擎及预编译组件兼容 | PyTorch CUDA 不可用、组件加载失败 |
| CUDA Toolkit | 需要构建 CUDA C/C++ 扩展时提供头文件和工具 | JIT 扩展无法构建 |
| nvcc | JIT 场景下能够编译对应 CUDA 源码 | `Could not find nvcc` |
| Triton | 与 Python、PyTorch、GPU 架构及内核实现兼容 | Triton 编译或执行失败 |
| FlashInfer 等内核库 | 支持当前 GPU、dtype、shape 和模型算子 | 无可用内核、后端初始化失败 |
| NCCL | 支持当前多卡或多机通信环境 | TP/EP 初始化或通信失败 |
| vLLM/SGLang | 支持目标模型、解码、量化和并行方式 | 模型未注册或功能不支持 |

只运行与环境匹配的预编译内核时，不一定需要完整 CUDA Toolkit；

是否必须安装 Toolkit，应由实际使用的后端和内核构建方式决定。

### 4.2 AOT、JIT 与首次启动要求

AOT（提前编译）和 JIT（运行时编译）对基础设施的要求不同：

```text
AOT：安装后直接加载预编译产物
     重点是预编译包与 GPU、CUDA、PyTorch 等环境匹配

JIT：安装或首次运行时生成适配当前环境的内核
     重点是编译器、头文件、nvcc、GPU 架构和缓存目录可用
```

首次启动明显变慢，不一定表示服务卡死，也可能是在执行：

- FlashInfer 等扩展编译；
- Triton 内核编译；
- Autotune；
- CUDA Graph 捕获。


### 4.3 软件版本兼容性

软件栈验收不能只记录“已经安装”，还要确认组合是否兼容。至少应固定并记录：

- Python 和系统编译工具版本；
- GPU 驱动版本；
- PyTorch 版本及其 CUDA 版本；
- vLLM/SGLang 版本；
- FlashInfer、Triton、NCCL 等组件版本；
- Transformers、Tokenizer 和多模态 Processor 依赖；
- JIT 场景下的 CUDA Toolkit 与 nvcc 版本。

升级其中一个组件可能改变其他组件的可用内核或构建结果。

### 4.4 模型与推理引擎适配


1. 当前引擎版本是否注册了 `config.json` 中的 `architectures`。
2. 是否支持该模型的权重布局、权重融合与并行切分。
3. 是否支持具体量化格式及相应 GPU 内核。
4. 是否支持自回归、投机或其他目标解码方式。
5. 是否支持所需的 KV Cache、Mamba/GDN 状态和前缀缓存路径。
6. 是否支持 Tokenizer、Chat Template 和多模态 Processor。
7. 是否支持计划的 TP、PP、EP 等并行方式。
8. 是否依赖开发分支、未合并 PR 或额外补丁。

`trust_remote_code` 可以帮助加载模型作者提供的 Python 参考代码，

但不能自动补齐推理引擎的原生模型执行器、连续批处理、分页 KV Cache、多卡权重切分、CUDA Graph 和专用 GPU 内核。

## 五、服务运行环境要求

### 5.1 容器与进程运行环境

如果服务运行在容器中，需要同时验证容器内外的资源视图和运行条件（作者暂未涉及，以下为理论指导）：

- GPU 和必要设备是否已正确映射，容器内能否看到预期 GPU。
- 容器中的驱动、CUDA、PyTorch 和推理引擎组合是否与镜像设计一致。
- `/dev/shm` 是否满足多进程通信和框架运行要求。
- 模型缓存、JIT 编译缓存和日志目录是否存在且可写。
- API 端口是否与已有进程冲突，容器端口映射是否正确。
- 文件描述符、进程数和内存等限制是否会提前终止服务。
- 容器重启后，模型和编译缓存是否按预期保留。


### 5.2 网络要求

推理服务至少需要分别检查业务网络和推理通信网络。

**业务网络**包括客户端到 API 的链路、端口、代理和流式响应。部署前应确认：

- `/health`、`/v1/models` 和生成接口的访问路径是否符合预期。
- 反向代理和网关是否支持长时间生成及流式输出。
- 各层超时是否匹配真实请求的最长处理时间。
- 流式响应是否被中间层不必要地缓冲。
- 多模态请求体大小是否受到额外限制。

**推理通信网络**用于多卡和多机执行。多机场景需要确认节点间连通性、NCCL 选择的网卡和接口、实际传输路径以及相关日志。

两类网络应分别验收：API 能访问不代表多机通信正常，多机通信正常也不代表客户端链路支持流式生成。

## 六、部署检查、验收与故障定位

### 6.1 部署前只读检查

查看 GPU、驱动和显存：

```bash
nvidia-smi
```

查看多卡拓扑：

```bash
nvidia-smi topo -m
```

查看 CPU、主机内存和磁盘：

```bash
lscpu
free -h
df -h
df -h /dev/shm
```

查看 PyTorch、CUDA 和 GPU 计算能力：

```bash
python - <<'PY'
import torch

print("PyTorch:", torch.__version__)
print("PyTorch CUDA:", torch.version.cuda)
print("CUDA Available:", torch.cuda.is_available())
if torch.cuda.is_available():
    for index in range(torch.cuda.device_count()):
        print("GPU", index, torch.cuda.get_device_name(index))
        print("Compute Capability:", torch.cuda.get_device_capability(index))
PY
```

查看 CUDA 编译工具：

```bash
command -v nvcc
nvcc --version
```

如果服务只使用预编译内核，找不到 nvcc 不一定阻止启动；如果当前后端需要 JIT 编译 CUDA 扩展，则应将其列为重点检查项。

查看模型架构和关键配置：

```bash
python - <<'PY'
import json

path = "/path/to/model/config.json"
with open(path, "r", encoding="utf-8") as file:
    config = json.load(file)

for key in (
    "architectures",
    "model_type",
    "auto_map",
    "quantization_config",
    "max_position_embeddings",
):
    print(key, config.get(key))
PY
```

检查 vLLM 模型注册表：

```bash
python - <<'PY'
from vllm.model_executor.models.registry import ModelRegistry

print(ModelRegistry.get_supported_archs())
PY
```

检查 SGLang 模型注册表：

```bash
python - <<'PY'
from sglang.srt.models.registry import ModelRegistry

print(ModelRegistry.get_supported_archs())
PY
```

注册表接口可能随版本调整；如果导入路径或调用方式发生变化，应以当前部署版本的代码和文档为准。


### 6.2 分阶段验收

将启动过程分阶段检查，比只看最后一条报错更容易定位问题。

| 启动阶段 | 主要工作 | 通过判据 |
|---|---|---|
| 环境初始化 | 设置 GPU 可见性，加载 Python、PyTorch 和推理引擎 | GPU 数量和型号符合预期，无基础依赖错误 |
| 配置解析 | 读取模型结构、量化、上下文和多模态配置 | 架构已识别，关键配置无冲突 |
| 输入组件加载 | 初始化 Tokenizer、Chat Template、Processor | 文件和依赖完整，能够处理样例输入 |
| 分布式初始化 | 创建 TP/PP/EP 通信组，初始化 NCCL | 所有预期 GPU 加入，无通信初始化失败 |
| 模型与权重加载 | 创建模块、读取分片、映射和切分权重 | 权重名称、shape、dtype 检查通过 |
| 状态池分配 | 测量剩余显存，分配 KV Cache 和其他状态 | 可用缓存和并发容量符合当前配置预期 |
| 内核选择与编译 | 选择后端，执行必要的 JIT 和 Autotune | 无内核缺失或编译失败 |
| CUDA Graph 与 Warmup | 捕获执行图，运行内部测试 | 完整前向和生成流程成功 |
| Ready 与真实请求 | 切换就绪状态，执行 API 验收 | 健康检查和真实生成均通过 |

排障时应记录失败发生在哪个阶段，并保留该阶段前后的日志。只根据最后一行异常更换 CUDA 或升级框架，容易扩大变更范围而仍未触及根因。

### 6.3 真实请求验收

服务进入 Ready 后，先检查基础接口。以下示例假设服务监听本机 `8000` 端口，实际使用时应替换地址和模型名：

```bash
curl -f http://127.0.0.1:8000/health
curl -f http://127.0.0.1:8000/v1/models
```

再发送一次流式生成请求：

```bash
curl -N http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "<model-name>",
    "messages": [
      {"role": "user", "content": "请用一句话介绍你自己。"}
    ],
    "max_tokens": 64,
    "stream": true
  }'
```

基础请求通过后，还应按模型能力验证：

- 非流式和流式输出是否一致符合预期；
- 多轮对话和 Chat Template 是否正确；
- 停止 Token 和 `max_tokens` 是否生效；
- 多模态输入和工具调用是否正常（如适用）；
- 请求中止后缓存和状态是否回收；
- 多并发下是否出现输出错乱、异常终止或资源持续增长；
- 长时间运行后是否仍能处理新请求。

多并发验收应使用接近真实业务的输入长度、输出长度和到达方式。一次短请求成功只能证明基本链路可用，不能代替生产容量验收。

### 6.4 常见报错与基础设施层级映射

| 报错或现象 | 优先排查层级 | 只读检查方向 |
|---|---|---|
| `Unsupported architectures` | 模型架构未注册 | 对比 `config.json` 与当前引擎模型注册表 |
| 启用 `trust_remote_code` 后仍无法启动 | 引擎缺少原生实现或目标功能 | 检查模型、解码、缓存和并行支持，而非继续修改启动参数 |
| `Could not find nvcc` | CUDA Toolkit/JIT 工具链 | 检查 nvcc 路径、版本及当前后端是否确实需要 JIT |
| `No compatible kernel` | GPU 架构、dtype、shape 或量化内核 | 核对 GPU 计算能力、模型精度和内核支持范围 |
| NCCL 初始化失败 | 多卡通信、驱动、网络或环境 | 检查 GPU 拓扑、网卡选择、节点连通性和 NCCL 日志 |
| 权重名称或 shape 不匹配 | 权重加载器或 checkpoint 布局 | 检查模型版本、分片完整性、量化格式和引擎实现 |
| `No memory for KV cache` | 显存分配与缓存配置 | 检查权重加载后的剩余显存、上下文和并发配置 |
| 最大并发被自动降低 | KV/Mamba 等状态池容量 | 检查缓存 Token 数、状态槽位和每请求状态占用 |
| Tokenizer/Processor 加载失败 | 输入处理组件或模型仓库文件 | 检查仓库文件、依赖版本和模型配置 |
| 健康检查通过但输出异常 | Chat Template、解码流程或数值正确性 | 用固定样例对比输入模板、输出和停止条件 |
| 首次启动特别慢 | JIT、Autotune、CUDA Graph | 检查启动日志、编译缓存和磁盘状态 |

这张表用于确定优先排查方向，不应代替完整日志分析。同一报错可能由多个因素触发，变更前应先确认失败层级。

### 6.5 完整决策流程与最终清单

一次完整的基础设施检查可以按以下顺序推进：

```text
模型、量化和解码方式是否被目标引擎支持？
        │
        ├── 否 → 更换受支持的模型变体、引擎或版本
        ▼
GPU 计算能力是否满足内核和精度要求？
        │
        ├── 否 → 更换 GPU、后端或模型变体，不能只升级 CUDA
        ▼
权重、缓存、状态和运行时资源是否足够？
        │
        ├── 否 → 调整容量目标、模型精度或硬件配置
        ▼
驱动、PyTorch、CUDA、内核库和编译工具是否匹配？
        │
        ├── 否 → 先确定不兼容组件，再评估变更
        ▼
多卡通信、主机资源、容器和网络是否满足要求？
        │
        ├── 否 → 修复对应基础设施层
        ▼
小上下文、低并发启动并完成正确性验证
        ▼
按真实长度和并发逐步验收
        ▼
形成已验证的版本组合、容量基线和检查记录
```

部署前最终核对：

- [ ] 已确认准确的模型版本、架构、量化格式和解码方式。
- [ ] 当前推理引擎版本已注册目标模型架构。
- [ ] 当前引擎支持所需多模态、状态和并行能力。
- [ ] GPU 型号、计算能力和 dtype 满足内核要求。
- [ ] 显存预算包含权重、缓存、状态、临时缓冲区和通信预留。
- [ ] 主机 CPU、内存、NUMA 和磁盘满足加载与运行要求。
- [ ] 驱动、PyTorch、CUDA、推理引擎和内核库版本组合已验证。
- [ ] JIT 场景所需 nvcc、编译工具和缓存目录可用。
- [ ] 多卡或多机通信路径已检查，无异常回退。
- [ ] API 链路已验证长请求和流式输出。
- [ ] 已记录软件版本、模型版本、配置和验收结果，能够据此复现环境。

大模型推理服务的基础设施建设，不是简单准备 GPU 和模型文件，而是对硬件能力、资源容量、软件依赖、模型实现和服务运行环境进行一次完整的兼容性验证。
