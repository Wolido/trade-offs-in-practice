# DeepInfer VS vLLM，区别在哪里？

> 目标：梳理 DeepInfer 与 vLLM 的差别，熟悉哪些能力来自 DeepSeek 模型与推理引擎的联合设计，哪些是对同类引擎的工程优化，对实际推理有何效果。

---

## 一、通用引擎和专用引擎

vLLM 是通用引擎，它的优化大多不依赖具体模型。例如，continuous batching 负责提高 GPU 利用率，PagedAttention 负责管理 KV cache，CUDA Graph 负责减少 decode 时的调度开销。

DeepInfer 走的是另一条路。它在 2026 年 10 月以 Apache-2.0 开源，从 vLLM 分叉而来，也吸收了 SGLang 的一些设计，但只服务 DeepSeek-V4.1-Flash，只面向 NVIDIA SM100 和华为昇腾 950，模型结构、算子和调度可以一起改

因此，DeepInfer 的改动可以分成两类：

- **模型和引擎一起设计**：输入计算可以走更短的路径，KV cache 可以跨层复用，缺失的局部 KV 可以只补一小段。
这些能力依赖 V4.1-Flash 的模型结构，vLLM 不能只靠调整调度参数获得。
- **通用机制做得更深**：异步调度、MoE 负载均衡、专用算子等，并非只有 DeepInfer 能做，
但它围绕单一模型和指定硬件做了更彻底的优化。

开源版需要注意两个问题。第一，开源 FlashMLA 少了一段手写优化，decode 性能比 DeepSeek 内部完整版低约 5%～10%，
不能把开源版本的测试结果直接当成线上版本。
第二，DeepInfer 没有 TP 路径，只使用 DP、EP 和 CP，它的多卡设计主要围绕专家并行展开。

---

## 二、前置概念

**Prefill 和 decode** 是推理的两个阶段。Prefill 一次处理整段输入，计算量大，主要影响首 token 时延（TTFT）；
decode 每次生成一个 token，需要反复读取模型权重，更容易受显存带宽限制，主要影响相邻 token 的间隔（TPOT）。

**KV cache** 保存历史 token 的 Key 和 Value，避免每次生成时重算整段上下文。它能减少计算，也会占用大量显存。

**投机解码** 先让成本较低的草稿一次猜出多个 token，再交给原模型验证。猜对的部分一次输出，同时保持原模型的输出分布，因此属于无损加速。
问题在于，猜得不准时，验证也会白白消耗算力。

**EP 和 DP** 都会在后文出现。EP 把 MoE 模型的专家放到不同 GPU 上；DP 部署多份模型副本，把请求分给不同副本处理。

## 三、Prefill阶段的优化

普通推理流程里，每个输入 token 都要完整经过模型。DeepInfer 围绕 V4.1-Flash 的结构，从三个地方减少了这部分开销。

### 3.1 CED：输入和输出不再走同样长的路径

V4.1-Flash 使用 Cross-Layer Early Decoding（CED）。decoder 需要的全局 KV，
可以直接由最后一层 encoder 的 hidden state 投影得到，不必让每个历史 token 再完整穿过全部 decoder 层。

坦白而言，处理输入时走一条较短的路径，生成回答时仍使用完整能力。最终，prefill 只激活约 8B 参数，decode 激活约 16B 参数。

这里的重点不是“8B 比 16B 小”，而是 prefill 和 decode 的计算路径可以不一样。这个收益首先来自模型结构，引擎负责把它落实成高效实现；换成不具备这种结构的模型，就不能直接照搬。

### 3.2 CSA2：全局 KV 不必每层重算

在普通 Transformer 中，不同层通常要分别计算自己的 KV。CSA2 允许全局 KV 跨层复用，
因此只需计算 4 次，而不是每层各算一次。

DeepInfer 又融合了相关推理 kernel，把单个复用层压缩到 prefill 15 个 kernel、decode 11 个 kernel。
前者减少重复计算，后者减少 kernel 启动和中间数据搬运，两层优化共同降低开销。

CSA2 解决的是全局 KV 的重复计算，下一节的 SWA Bounded Replay 解决的是局部 KV 的补算问题。

### 3.3 SWA Bounded Replay：缓存没接上的地方，只补最近 128 个 token

多轮对话和 Agent 请求经常能命中前缀缓存，但缓存不一定完整。如果中间缺了一段，常见做法是重新计算相关前缀；
上下文越长，补算成本越高。

V4.1 的前若干层使用滑动窗口注意力（SWA），每个 token 只看最近 128 个 token，窗口外的 KV 本来就用不到。
DeepInfer 只重放最近 128 个 token，用它补齐当前计算所需的局部信息，不再重算整段前缀。
窗口的好处是局部 KV 不用持久化，上一代版本要把每层的窗口 KV 全写到 SSD，使用的时候得现场重建。

这样，补算成本就从“随上下文长度增长”变成了“最多处理固定的 128 个 token”。长上下文、缓存部分命中的场景，收益尤其明显。

## 四、Decode 阶段的优化

### 4.1 DSpark：草稿长度不固定

常见的投机解码会固定草稿长度：每轮先猜 N 个 token，再统一验证。草稿质量高时很划算，质量低时也会付出同样的验证成本。

DSpark 改成半自回归草稿生成，并根据置信度决定验证多少、验证哪些。把握较大的草稿多利用，把握不足的草稿少浪费验证算力。
它主要面向 Agent 负载中常见的小批量 decode，并配套完整的 CUDA Graph 解码路径。

DSpark 还与前面的 SWA 重放共用回溯边界，模型结构、缓存和 decoding 策略在这里不是三套独立设计，而是相互配套的。

### 4.2 异步调度

如果 CPU 组织 batch 时 GPU 只能等待，decode 每一步之间就会出现空档。batch 越小、单步执行越快，这类空档越明显。

DeepInfer 默认开启异步调度，让 CPU 的批组织与 GPU 执行重叠，减少等待。
它与 vLLM 要解决的问题相同，区别在于 DeepInfer 可以围绕固定模型和完整 CUDA Graph 路径，把调度器做得更专用。

### 4.3 结果一致性

浮点计算的归约顺序可能随 batch 组合变化，因此同一个输入在不同 batch 中运行，结果可能略有差异。平时不一定明显，但会给评测复现和回归测试带来麻烦。

DeepInfer 提供批不变推理和确定性采样。开启后，同一个输入无论与哪些请求拼批，输出都保持一致；
再配合固定随机种子，可以做到“同输入、同输出”。目前确定性采样仅支持 NVIDIA。

这项能力要求调度、算子和采样流程一起控制浮点行为，不是单独改一个采样参数就能完成的。

## 五、其余工程优化

前面几项优化依赖模型结构，接下来的改动更接近传统推理引擎优化：算子更专用，通信更适合 MoE，调度开销更低。

### 5.1 算子围绕 MLA、FP8 和 MoE 定制

| 组件 | 解决的问题 | DeepInfer 的做法 |
|---|---|---|
| FlashMLA | MLA 注意力计算 | 原生面向 MLA 开发，而不是在通用注意力实现上后续适配 |
| DeepGEMM | FP8 矩阵乘 | 核心约 300 行，使用 JIT 编译，支持 dense 和两种 MoE 布局 |
| DeepEP | MoE 专家间通信 | 分别为高吞吐和低延迟 decode 提供 kernel，支持 FP8 dispatch 及计算通信重叠 |
| TileKernels / DeepSelect | MoE 路由和 top-k 选择 | 直接处理 BF16，省去先转 FP32 的步骤 |

这些设计的共同点，是围绕 V4.1-Flash 的 MoE 布局、MLA 结构和 FP8 缩放方式实现，尤其重视小批量 decode 的延迟，
而不是直接复用训练或通用推理算子。

### 5.2 不走 TP，重点解决专家并行的负载不均

vLLM 支持 TP、PP、DP、EP 等多种并行方式。DeepInfer 没有 TP，主要使用以下组合：

- **EP + EPLB**：专家并行配合负载均衡，默认复制 32 个冗余专家。某个专家过热时，可以用其他 GPU 上的副本分担请求，避免少数专家拖慢整批计算；
- **Attention DP / 均衡 CP**：注意力部分使用数据并行，长上下文则使用均衡的上下文并行，减少 TP 对高速互联的依赖。

这条路线更看重 MoE 模型在高并发下的吞吐和扩展效率，代价是放弃了 TP 降低单请求时延的优势。
它不是全面优于 TP，而是针对目标模型和负载作出的取舍。

## 六、DeepInfer 的价值

| 层面 | 主要改动 | 是否依赖 V4.1-Flash |
|---|---|---|
| 输入计算 | CED 让 prefill 走较短路径，激活约 8B 参数 | 是 |
| KV 计算与补算 | CSA2 全局复用；SWA 只重放最近 128 个 token | 是 |
| 投机解码 | DSpark 按置信度调整验证 | 与模型及解码流程紧密相关 |
| 调度与复现 | 异步调度、批不变推理、确定性采样 | 主要是工程实现 |
| 算子与通信 | FlashMLA、DeepGEMM、DeepEP、DeepSelect | 可借鉴，但需要适配其他模型 |
| 多卡扩展 | EP + EPLB，Attention DP / 均衡 CP，不提供 TP | 通用思路，专用实现 |

所以，DeepInfer 并不意味着 vLLM 的路线过时了。vLLM 的优势仍是模型覆盖、生态和部署通用性。DeepInfer 则展示了模型、算子、缓存和调度一起设计后，单一模型还能继续挤出多少性能。
