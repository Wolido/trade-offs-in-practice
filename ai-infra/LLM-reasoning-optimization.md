# 大模型推理优化与负载均衡

> 目标：理解大模型推理部署的完整决策链条——从硬件能力出发，经模型选择与量化、框架与并行策略、负载均衡，到推理优化的原理与取舍依据。

---

## 一、识别硬件环境

### 1.1 GPU 卡类型：显存、算力与精度支持

部署推理服务前，首先要对 GPU 建立三个维度的认识：

**显存容量**决定能放多大的模型和多少并发，**算力**决定 prefill 阶段的吞吐上限，**显存带宽**决定 decode 阶段的单请求时延下限。这三者共同划定了部署方案的可行域。

GPU 支持的数值精度直接决定量化方案的选择，这一点常被忽略但非常关键：

**FP8 Tensor Core**从 Hopper 架构和 Ada 架构（L4/L40S）才开始支持，更早的卡无法运行 FP8 量化模型；

**INT8 W8A8 **量化从 Turing 起普遍可用；只压缩权重的 W4A16 方案（AWQ/GPTQ）对硬件没有要求，任何卡都能运行，但高性能的 Marlin 反量化 kernel 需要 Ampere 架构及以上。

因此"想跑某个量化模型"之前，必须先确认卡架构是否具备对应的计算单元。

GPU 架构代际与支持量化精度的对照关系如下：

| 架构代际 | 计算能力 | 代表卡型 | FP16 张量核 | BF16 | INT8 (W8A8) | FP8 (W8A8) | FP4 (NVFP4) | W4A16 (Marlin 加速) |
|---|---|---|---|---|---|---|---|---|
| Turing (2018) | SM 7.5 | T4、RTX 2080 | ✓ | ✗ | ✓ | ✗ | ✗ | 可运行，无加速 |
| Ampere (2020) | SM 8.0 / 8.6 | A100/A800、RTX 3090 | ✓ | ✓ | ✓ | ✗ | ✗ | ✓ |
| Ada Lovelace (2022) | SM 8.9 | L4、L40S、RTX 4090 | ✓ | ✓ | ✓ | ✓ | ✗ | ✓ |
| Hopper (2022) | SM 9.0 | H100/H200/H800 | ✓ | ✓ | ✓ | ✓ | ✗ | ✓ |
| Blackwell (2024) | SM 10.0 / 12.0 | B200/GB200、RTX 5090 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

三点提示：

第一，BF16 是当代开源模型的默认权重精度，Turing 是唯一不支持 BF16 的代际，遇到老卡需确认模型能否以 FP16 运行；

第二，FP8 的分水岭在 Ada/Hopper——A100 虽然算力强大但跑不了 FP8 量化模型，这是 A100 集群部署时最常见的选型误区；

第三，W4A16 方案"任何卡都能跑"指的是功能层面，Turing 卡能运行但没有 Marlin 高性能 kernel 的加速，低并发下的提速收益会打折。


### 1.2 显存瓶颈还是算力瓶颈

大模型推理分为两个阶段。**Prefill 阶段**一次性处理整个输入 prompt，此时矩阵尺寸大、计算密度高，算术强度远超 GPU 的算力/带宽比值，tensor core 被打满，是**算力瓶颈**。所需算力可以用下式估算：处理 N 个 token 的 prompt 约需 2 × 参数量 × N 次浮点运算。

**Decode 阶段**逐 token 生成，每生成一个 token 都要把模型的全部权重从显存（HBM）完整读取一遍。以一个 27B 参数的 BF16 模型为例，权重约 54 GB，目标 50 token/s 所需带宽约 2.7 TB/s——已经超过单张 A100 的 2 TB/s，需要两张卡才能喂满，此时瓶颈完全在显存带宽。

这个分析得出核心经验法则：**低并发时看带宽，高并发时看算力**。单请求或小 batch 的时延由 HBM 带宽决定，这也是为什么权重减半的量化模型在低并发下反而比 FP16 更快；而当 batch 足够大时，权重的读取成本被所有请求摊薄，瓶颈转移到 tensor core 的算力上，此时量化带来的反量化开销反而成为净损失。

### 1.3 通信架构：NVLink 与跨节点网络

多卡部署绕不开通信问题，而通信能力的数量级差异决定了并行策略的边界。

**机内互联（NVLink）**：张量并行（TP）要求同一层的计算结果在多个 GPU 间频繁交换，对互联带宽极其敏感。没有 NVLink 的卡应当避免张量并行，转而采用"一卡一实例"的部署方式。

**跨节点网络（RDMA/InfiniBand）**：节点间的典型互联是IB 或 RoCE 网卡，比机内 NVLink 低一个数量级以上。

因此有一条硬规则：**张量并行应限制在单个 NVLink 域（通常是单台服务器）之内**。跨节点只应使用流水线并行（PP）或数据并行（DP）。


### 1.4 小结

硬件摸底最终收敛为三条判断：

第一，卡的显存和带宽决定了"什么规模的模型、以什么量化精度、能支撑多少并发"；

第二，卡架构（Turing/Ampere/Hopper/Ada/Blackwell）决定了可用的量化方案集合；

第三，NVLink 和 RDMA 的存在与否与速率高低，决定了并行策略只能在什么范围内选择。

## 二、选择要部署的模型

### 2.1 显存需求的完整计算

模型部署的第一道算术题是：目标模型在给定并发下需要多少显存？

**模型权重**：参数量 × 每参数字节数。BF16/FP16 为 2 字节，FP8/INT8 为 1 字节，INT4 为 0.5 字节。
27B 模型的 BF16 权重约 54 GB，INT4 量化后约 13.5 GB。

**KV Cache**：推理过程中为避免重复计算而存储的历史 Token 的 Key 和 Value 张量。它是推理阶段显存占用的最大动态变量，直接决定了在给定显存下能支持多大的并发（Batch Size）和多长的上下文（Context Length）。

```
KV Cache Size = 2 × Transformer层数 × KV 头数 × 每个头的维度 × 上下文长度 × 数据精度字节数 
```

**框架开销与预留**：推理框架自身、CUDA context、CUDA Graph 捕获等合计约 2~4 GB，需要在预算中预留。

把三部分相加，再对照 GPU 显存，就能判断"放不放得下"。放不下的常规解法按优先级是：换量化精度、换更大显存的卡、加卡做并行。

### 2.2 量化模型选择

当显存不足而仍希望运行某个模型时，量化是主要手段。量化方案按"量化什么"分为两大类。

***权重量化（W4A16，代表：AWQ、GPTQ）（推荐）**：磁盘和显存中存放 4bit 权重，计算前在 GPU 内反量化回 FP16，再与 FP16 激活做矩阵乘。它的性能逻辑与第一节的瓶颈分析直接相关：decode 阶段每生成一个 token 要把全部权重读一遍，权重减半意味着带宽占用减半，因此**在低并发下量化模型比 FP16 更快**——这是反直觉但正确的一个结论，量化引入的额外计算开销远小于它省下的权重读取时间。但当并发升高，权重读取成本被大量请求摊薄，瓶颈转移到算力侧，反量化的计算开销成为净损失，此时 W4A16 与 FP16 打平甚至略输。精度方面，由于激活保持 FP16，量化对模型能力的影响通常很小，校准过程也相对简单。

**权重+激活量化（W8A8，代表：FP8、INT8 smoothquant、compressed-tensors）**：权重和激活都量化为 8bit，直接以 8bit 数据走 tensor core 计算，累加到 FP32/FP16。由于不需要反量化且数据位宽减半，等效算力相对 FP16 接近翻倍，因此它天然适合**高并发、算力瓶颈**的场景。代价是激活量化对精度的伤害大于权重量化，且需要校准数据；FP8 仅 Hopper/Ada 及以后的卡可用，INT8 通用。更激进的 W4A8（4bit 激活）等方案目前尚不成熟，生产环境慎用。

两类方案的对照可以总结为：**低并发选 W4A16（用带宽换时延），高并发选 FP8 W8A8（用精度风险换算力），精度伤害从小到大大致是 W4A16 ≈ FP8 < INT8 W8A8**。量化版本的来源优先级为：官方发布 > 官方认证的社区量化 > 其他高下载量版本；上线前应在自己的评测集上对比 FP16 基线的退化幅度，一般要求损失在 1~2 个百分点以内。

## 三、后端推理框架与并行策略

### 3.1 主流推理框架：vLLM 与 SGLang

两大主流开源框架都采用 continuous batching（连续批处理）作为核心调度机制：与传统的静态 batching 不同，它允许新的请求随时插入当前正在执行的 batch，已完成的请求随时退出，从而把 GPU 的利用率维持在高位。两者都提供 OpenAI 兼容的服务接口，在模型覆盖、结构化输出、多模态支持上互有长短且差距快速缩小。真正的差异化在前缀缓存的实现上。

**vLLM** 实现了块级别的 prefix caching，把 KV cache 按固定大小的块管理，命中相同前缀时直接复用已缓存的块。

**SGLang** 的 RadixAttention 则把整个前缀空间组织为一棵基数树，系统性地最大化任意前缀的重用——在多轮对话、agent 工具调用这类大量请求共享长 system prompt 或历史上下文的负载下，RadixAttention 的缓存命中率和由此带来的吞吐优势通常更明显。

实践上的选型建议是：默认从生态更广泛的 vLLM 起步；当负载特征以多轮前缀复用为主时，用同一模型对两个框架做对比压测，用 TTFT、TPOT和吞吐数据做最终决定。

### 3.2 并行策略

**张量并行（TP）**：把单个权重矩阵横向切分到多块 GPU，每块计算部分结果，再通过 AllReduce 合并。优点是单请求的时延最优——一个请求可以同时动用多卡的算力和带宽之和；代价是通信密集（每层两次 AllReduce），因此对互联带宽极其敏感。结论是 TP 只应在 NVLink 域内使用，且 TP 越大 scaling 效率越低（TP=8 在 NVLink 内约 75~85%），应在"放得下模型"的前提下取最小的 TP。

**序列并行（SP）**：把序列维度切分到多卡，用于分摊那些无法按 TP 切分的激活（LayerNorm、Dropout 等）的显存占用。它与 TP 是正交的显存优化，使用 TP 时应当始终同时启用，现代框架已默认将其并入 TP 实现，无需单独决策。

**流水线并行（PP）**：把模型按层纵向切分，连续的层组成不同的 stage，每个 GPU 只持有自己 stage 的权重，stage 之间点对点传递中间激活。通信量远小于 TP 的 AllReduce，因此是跨节点部署超大模型的可行方式。适用场景：模型单层放不进单卡，或必须跨节点部署。

**数据并行（DP）**：部署多个完全独立的模型副本，由路由层把请求分流。副本之间没有任何额外通信，scaling 效率最高。**扩展吞吐量的首选方式是多实例加负载均衡，而不是把单个实例的 TP 拉到最大**。

**专家并行（EP，MoE 模型特有）**：对 DeepSeek、Qwen3-MoE 这类混合专家模型，可以把专家网络切分到不同卡上（EP），注意力层仍按 TP 组织。现代框架支持 DP+EP 的组合调度，对 MoE 模型而言，这种组合在高并发下的吞吐显著优于纯 TP 方案，因为不同请求的 token 可以被路由到不同专家上实现负载的自然均衡。

组合策略可以参考如下归纳：

单机能放下的模型用尽量小的 TP；单机放不下的稠密模型用机内 TP 或跨机 PP；MoE 大模型用机内 TP/EP 组合；纯粹为了扩吞吐就用多个独立实例加负载均衡。

## 四、推理负载均衡

### 4.1 先单实例后均衡

负载均衡的前提是正确理解它的动机。单实例的 continuous batching 已能把单卡利用率打到 85% 以上，所以增加实例做负载均衡的三个真实价值是：**故障转移**（任一实例宕机不影响服务）、**滚动升级**（摘流量、升级，实现不停机变更）、以及**突破单实例的调度上限**。

如果一个实例的 GPU 利用率还很低而请求在排队，问题通常在调度参数而非容量，应先调优再扩容。

### 4.2 路由策略

**无状态路由**（轮询、最少连接）是最基础的方案，配合带生成能力探测的深度健康检查，以及足够长的超时时间。

**前缀缓存亲和（cache-aware routing）**是多轮对话与 agent 负载的关键优化，其原理是：把共享相同前缀的请求尽量路由到同一实例，使该实例的前缀缓存（vLLM 的 prefix caching 或 SGLang 的 RadixAttention）命中，从而省掉重复 prefill 的计算和时间。实现路径按工程成本从低到高有三层：

应用层按会话 ID 做一致性哈希（简单易上手，实践可行）；

使用框架自带的路由组件（vLLM 和 SGLang 提供了基于负载与前缀相似度的现成路由方案，网上可查）；

自研 token 级的前缀亲和调度（难度大，对开发水平要求高）。

**PD 分离（Prefill/Decode 分离）**：prefill 吃算力、需要前缀缓存，decode 吃显存带宽、需要大量 KV cache 显存。把它们拆到不同的节点池上，各自独立扩缩容，通过高速传输层在 prefill 完成后把 KV cache 传递给 decode 节点。代价是架构复杂度大幅上升（多一跳 KV 传输、调度器要管两个池），因此适用门槛一般是数百以上并发、prompt 长度差异大的场景；中小规模用实例级负载均衡即可。（只是提供个思路，还没实践过）


## 五、推理优化

### 5.1 通信网络优化

通信优化的核心目标是让并行计算等待数据的时间最小化。机内确保张量并行限定在 NVLink 域内；跨节点确保 RDMA（IB/RoCE）与 GPUDirect RDMA 生效，使数据不经过 CPU 内存直接在网络与显存间搬运。NCCL 层的调优要点是正确指定网卡与接口，并在日志中确认没有出现回退到低速 socket 传输的告警。NUMA 亲和对 PCIe 卡和多路服务器的性能有可见影响。

### 5.2 推理参数与运行时优化

#### 5.2.1 vLLM推理引擎
**调度参数**：max_num_seqs（单步最大并发序列数）与 max_num_batched_tokens（单步 prefill 的最大 token 数）是最直接的两个旋钮。前者调大提升吞吐但拉长单请求的 token 间隔，后者决定长 prompt 被分块处理的粒度，影响首 token 时延与 decode 插队之间的公平性。两者的合理取值需要根据生产环境的任务情况来确定，压测后找到一个临界值。

**前缀缓存**：应始终开启，尤其在多轮对话与 agent 场景，它是零成本的最大优化项之一。

**CUDA Graph**：把固定 batch 档位的 kernel 序列捕获为图，消除逐 kernel 调度的 CPU 开销，对 decode 阶段有 20% 以上的稳定收益，现代框架默认开启。仅在调试期需要禁用。

**投机采样（speculative decoding）**：用一个小草稿模型一次预测多个后续 token，再由原模型并行验证，接受的 token 一次性输出。因为验证步骤保持了与原模型完全一致的输出分布，这是**无损**加速。代价是草稿模型占显存，且高并发下算力本就饱和，投机带来的额外计算反而降低吞吐——所以它最**适合低并发**的在线服务。

**KV cache FP8**：把 KV cache 也量化为 FP8，显存占用减半意味着并发上限或上下文长度上限直接翻倍，精度损失在长上下文实测中通常可忽略，是显存紧张时的首选释放手段。

**采样与输出参数**：max_tokens 的设定对容量有实际影响——设得过大（默认值常为数 K）会让少量长生成请求占据大量 KV cache，应按业务实际的 P99 生成长度设定。结构化输出约束优先选用专门的结构化解码后端，比通用正则约束开销更低。

### 5.3 压测与验证

上线前必须用压测建立基线。核心验收指标有四个：**TTFT**（首 token 时延，长 prompt 场景主要由 prefill 决定，看 P99 而非均值）、**TPOT**（token 间间隔，直接受并发调度参数影响）、**单实例输出吞吐**（压到 GPU 利用率 85% 以上后即为该配置的实际上限）、**前缀缓存命中率与 KV cache 占用率**。压测应在接近真实业务的请求长度分布和到达速率下进行，固定 QPS 的压测比最大压力压测更能暴露 P99 问题。

## 六、完整决策流程

综合全文，一次完整部署的推理过程是：

先摸清硬件——卡的显存、带宽、算力三要素与互联拓扑；

再选模型——参数量与注意力架构共同决定权重与 KV cache 的显存预算；预算不够则进入量化决策；

然后定并行策略——TP 限定在 NVLink 域内，跨节点用 PP，扩吞吐靠多实例 DP；

接着选框架并开启核心优化——前缀缓存，低并发叠加投机采样，显存紧张叠加 KV Cache ；

再在其上构建负载均衡；

最后以 TTFT/TPOT P99、吞吐、缓存命中率和 KV 占用四项指标压测验收。
