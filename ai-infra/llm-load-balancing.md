# 大模型多实例负载均衡：构建高并发、高可用推理服务

> 目标：理解大模型负载均衡与普通 Web 负载均衡的差异，完成从多实例架构、路由策略、健康与过载控制，到网关高可用的完整设计。

---

## 一、为什么大模型需要不同的负载均衡

### 1.1 普通 Web 负载均衡为什么不完全适用

普通 Web 服务通常可以把请求近似看成短连接、无状态、成本相近的任务。在这种前提下，轮询、最少连接和源 IP 哈希已经能够解决大部分分流问题。大模型推理却不满足这些假设。

第一，**请求成本不均匀**。两个请求都只占一个连接，但一个可能包含几百个输入 token、生成几十个输出 token，另一个可能包含数万 token 的长上下文并持续生成数分钟。只统计请求数或连接数，无法反映真实的 prefill 计算、decode 计算和 KV Cache 占用。

第二，**实例具有动态状态**。推理框架通过连续批处理动态处理请求，实例的 `running`、`waiting`、KV Cache 使用率和抢占情况会持续变化。同样都是 8 个运行请求，输入长度、输出长度和剩余工作量可能完全不同。

第三，**前缀缓局部性**。vLLM 的 prefix caching 和 SGLang 的 RadixAttention 都依赖实例本地状态。同一会话被路由到原实例，可以复用已有前缀；切换到其他实例则可能需要重新执行 prefill。因此，绝对平均地分配请求并不一定带来最低延迟。

第四，**流式请求持续时间长**。SSE 响应可能持续几十分钟，首 token 已经返回后连接仍然不能随意中断。普通Web短连接服务常用的超时、重试等方式不能直接照搬。

第五，**生成请求方式不同**。连接建立前的失败通常可以安全重试，但请求已经被后端执行后，因读取超时切换到另一实例，可能重复消耗 GPU，并对带有工具调用或业务副作用的 Agent 请求造成重复执行。

因此，大模型负载均衡的目标不是把请求数分得最平均，而是**在满足业务关键指标的前提下，平衡计算负载、排队时间和缓存复用，并在故障时提供明确、可验证的降级行为**。

### 1.2 多实例负载均衡解决什么问题

多实例负载均衡主要有三个价值。

**突破单实例上限**。单实例的连续批处理可以提高 GPU 利用率，但其并发仍受显存、KV Cache、调度参数和计算能力限制。多个独立实例通过数据并行扩展吞吐，通常比无限增大单实例张量并行规模更直接。

**支持故障转移**。某个实例进程异常或某台 GPU 主机下线时，新请求可以被分配到其他健康实例，而不是让整个服务入口失败。

**支持滚动升级**。实例可以先停止接收新会话，等待存量流式请求结束，再完成升级和恢复，避免直接切断全部连接。

负载均衡也有明确边界。如果单实例 GPU 利用率仍然很低，请求却已经排队，应优先检查`max_num_seqs`、`max_num_batched_tokens`、KV Cache 和请求长度分布等指标，而不是直接增加网关或实例。负载均衡可以分配流量，但不能修复单实例内部的低效调度。

## 二、基于 OpenResty + Lua 的多实例推理服务架构

### 2.1 总体架构

一个可运维的多实例推理服务，通常由入口高可用（暂未做 VIP）、负载均衡、状态采集、实例池和可观测性五部分组成。

这套架构的核心是**控制面与数据面分离**：

**请求数据面**负责处理实际业务流量。客户端请求到达后，OpenResty 先识别会话，再结合实例当前状态选择后端，最后将请求转发到对应的 vLLM 实例。

**状态控制面**负责维护路由所需的信息。后台任务定期读取各实例的监控指标，更新运行请求数、临时预留量和实例可用状态，为后续请求提供选路依据。

两条链路通过共享内存中的三类状态关联：

- **会话映射**：记录某个会话此前被分配到了哪个实例；
- **实例负载**：记录各实例正在处理的请求数，以及刚分配但尚未反映到监控指标中的请求数；
- **实例状态**：记录实例当前是否允许接收新请求。


### 2.2 一次请求经过的完整路径

结合实践，一次 `/v1/chat/completions` 请求按以下顺序处理：

1. **建立会话标识的兜底值**  
   请求进入后，先将客户端 IP 作为默认会话标识。即使后续无法从请求体中提取有效内容，也仍然可以完成路由。

2. **尝试生成更准确的会话指纹**  
   OpenResty 读取请求体，查找第一条用户消息。如果能够提取到有效内容，就根据内容生成会话指纹，用它替代默认的客户端 IP。这样，来自同一客户端的不同会话有机会被区分，同一用户的后续请求也有机会回到原实例。

3. **查询是否存在历史会话映射**  
   系统根据会话指纹查询共享内存。如果该会话此前已经分配过实例，就优先检查原实例；如果没有记录，则按新会话处理。

4. **判断原实例是否仍然适合接入**  
   对于老会话，系统检查原实例是否在线，以及当前负载是否低于设定阈值。原实例可用且未过载时，继续沿用原实例，以复用其本地前缀缓存；原实例已下线或过载时，则重新选择其他实例。

5. **为新会话或改迁会话选择最闲实例**  
   系统遍历当前可接入的实例，比较“正在处理的请求数”和“刚分配但尚未被监控指标反映的请求数”之和，选择综合负载最低的实例。临时预留量用于减少监控更新间隔内，多个新会话同时集中到同一实例的问题。

6. **更新会话映射和临时负载**  
   每次发生新分配或会话改迁，系统都会增加目标实例的临时预留量，并更新会话与实例的对应关系。会话映射有效期为 30 分钟，后续请求命中时会重新计时。

7. **将请求转发到目标实例**  
   完成选路后，OpenResty 将请求转发到选定的 vLLM 实例，并按照大请求体、长时间连接和 SSE 流式响应的要求处理转发过程。

8. **后台持续更新实例状态**  
   与此同时，后台任务定期采集各实例的运行请求数，并根据负载调整实例是否参与后续分配。新到达的请求使用最新状态进行选路，已经建立的流式连接则继续由原实例处理。

### 2.3 基础运行方式

OpenResty 的运行方式决定了它能够同时处理多少连接，以及不同工作进程之间如何共享路由状态。当前主要配置可以概括为：

| 能力 | 当前方式 | 在方案中的作用 |
|---|---|---|
| 工作进程数量 | 根据运行环境自动确定 | 多个工作进程共同处理请求，并通过共享内存交换路由状态 |
| 单工作进程连接上限 | 10240 | 限制每个工作进程能够同时维护的连接数量 |
| 会话状态存储空间 | 64 MB | 保存会话与后端实例之间的对应关系 |
| 负载状态存储空间 | 8 MB | 保存各实例的运行请求数和临时预留请求数 |
| 后端状态共享区域 | 128 KB | 支持查询和调整后端实例是否参与请求分配 |
| 被动故障判定 | 10 秒内失败 3 次 | 根据实际转发失败情况识别异常后端 |

单个工作进程支持 10240 个连接，并不等于系统能够同时执行 10240 个推理请求。

一个推理请求通常同时占用客户端连接和后端连接，而真正的推理并发还受到 vLLM 调度能力、KV Cache 容量以及实例负载阈值的限制。

### 2.4 三类共享状态分别解决什么问题

#### 会话状态：让多轮请求尽量回到原实例

系统为每个会话保存一条映射记录，主要包括：

- **会话标识**：优先根据第一条用户消息的部分内容生成指纹，提取失败时使用客户端 IP；
- **目标实例**：记录该会话此前被分配到的后端实例；
- **有效时间**：最近一次请求后保留 30 分钟。

每次老会话再次命中，或者会话被迁移到新实例，有效时间都会重新计算。因此，这是一条**随请求滑动续期**的记录，而不是从首次请求开始固定 30 分钟后删除。

会话状态的作用是提高前缀缓存复用率，但它只影响后续新请求，不会改变已经建立的流式连接。

#### 负载状态：判断哪个实例相对更闲

系统为每个实例保存两类负载信息：

1. **运行请求数**：最近一次从实例监控指标中采集到的、正在处理的请求数量；
2. **临时预留请求数**：已经分配给该实例，但尚未反映到最近一次监控指标中的新请求数量。

选路时，将两者相加得到实例的综合负载。数值越低，实例越容易被新会话选中。

#### 可用状态：决定实例能否参与分配

除了负载数值，系统还维护每个后端实例是否允许接收新请求的状态。

负载数值和可用状态承担不同职责：

- **负载数值**用于比较实例之间谁更闲；
- **可用状态**用于决定实例是否有资格参与本轮选择。

一个实例即使负载很低，只要已被标记为不可用，就不会参与正常选路；反之，实例可用也不代表它一定适合接入，还需要继续检查负载是否达到阈值。

### 2.5 后端列表与实例顺序的关系

当前方案中，后端实例被描述了两次：

- 后端实例池负责声明有哪些实例可以接收请求；
- 后台采集列表负责说明如何访问每个实例的监控接口。

监控采集通过实例地址找到目标，而动态调整实例状态时，当前实现使用实例在列表中的位置进行定位。因此，两处列表的顺序必须严格一致。

这种设计的实现成本较低，但存在明显的顺序耦合：增删实例或调整声明顺序时，如果只修改其中一处，可能把某个实例的负载状态错误地应用到另一个实例上。

## 三、路由设计：从会话识别到实例选择

路由层的任务不是单纯寻找空闲实例，而是在会话亲和、实例负载和故障转移之间进行有优先级的选择。设计时可以将决策过程固定为四个环节：**生成会话标识、判断原实例是否可继续使用、必要时重新选择实例、更新会话映射与临时负载**。以下按这一顺序展开。

### 3.1 请求接入：先建立可回退的会话标识

会话标识应采用“默认可用、按需增强”的设计。请求到达后，先将客户端 IP 作为默认标识，保证请求体无法解析时仍然能够完成路由；随后再尝试读取第一条用户消息，根据内容生成更准确的会话指纹。

无论消息直接使用文本内容，还是将文本放在结构化内容块中，系统都会提取第一段文本参与计算。为了控制处理成本，只取消息开头约 4096 字节生成指纹，而不处理完整消息。这样可以在不修改客户端的情况下，为多轮会话提供一定程度的粘滞能力。

设计时需要明确这种方案的边界：

1. 请求中没有可识别的用户消息时，只能使用客户端 IP；
2. 请求体超过约 8 MB 后，内容可能写入临时文件，当前实现无法继续从中提取指纹；
3. 复杂转义、多模态内容或不同的字段结构，可能导致提取结果不稳定。

因此，内容指纹只能作为**帮助路由器判断会话关系的提示信息**，不能视为严格、唯一的会话身份。它适合作为客户端暂时无法提供显式会话 ID 时的兼容方案。

### 3.2 老会话：缓存亲和不能越过可用性与负载约束

对于存在历史映射的老会话，路由设计应优先保留原实例，以复用其实例本地的前缀缓存。但在继续转发前，必须同时确认两个条件：

- 原实例当前允许接收新请求；
- 原实例的综合负载低于设定阈值。

两个条件同时满足时，请求继续发往原实例，并将会话映射的有效期延长到最近一次请求后的 30 分钟。任一条件不满足时，则为会话重新选择实例，并将映射更新为新目标。

负载判断同样适用于老会话。即使后台任务尚未将高负载实例标记为不可用，只要其实际负载与临时预留量之和已经达到阈值，下一次同会话请求仍会触发迁移。也就是说，**会话亲和是优先策略，但不是必须保持的硬性约束**。

这一过程只影响新到达的请求。已经开始的流式响应不会因为一次新的选路判断而被主动迁移。

### 3.3 新会话与改迁会话：从可用实例中选择最闲节点

对于没有历史映射的新会话，以及需要迁移的老会话，系统遍历当前可接入的实例，比较它们的综合负载，并选择数值最低的一个。选定目标后，本次动态计算出的实例替代默认的后端分配结果，请求随后被转发到该实例。

这一策略还需要考虑两种特殊情况：

- **多个实例负载相同**：当前实现保留列表中靠前的实例。因此，在低并发、各实例负载相同的情况下，请求可能优先集中到靠前的实例。这有利于集中前缀缓存，但不保证请求数量在所有实例之间均匀分布。
- **所有实例均不可用**：当前实现尝试回退到列表中的第一个实例。这只是避免无法生成路由目标的兜底行为，不代表集群仍有可用容量，也不能视为可靠的全故障处理机制。

因此，“选择最闲实例”解决的是正常状态下的分配问题，不能替代全忙、全故障场景的容量与降级设计。

### 3.4 临时预留：补偿监控更新的时间差

仅根据运行请求数选择实例，会受到监控更新间隔的影响。例如，实例 A 刚刚被选中，但它的监控数据尚未更新。此时其他请求仍然看到 A 的旧负载，并可能继续将新会话分配给它，短时间内造成请求扎堆。

为避免多个请求基于同一份过期状态重复决策，可以在路由层引入临时预留机制：

1. 新会话或改迁会话选中某个实例后，立即为该实例增加一份临时预留；
2. 后续请求计算综合负载时，将这部分预留计算在内；
3. 原实例的分数因此升高，后续请求更倾向于选择其他实例；
4. 不同工作进程更新预留量时采用原子操作，避免并发修改导致计数丢失。

当前实现不会在每个请求结束时扣减预留量，而是在下一次成功采集该实例监控数据后，将其临时预留量直接清零。

因此，临时预留只是**两次监控采样之间的短期补偿**，不是精确的在途请求数。它不需要跟踪每个请求的完整生命周期，但在清零时也无法区分哪些请求已经进入运行状态、哪些请求失败、哪些请求尚未到达后端。

### 3.5 状态更新：区分保持粘滞与重新分配

路由完成后，需要同步维护会话映射和临时预留。不同场景下的处理方式如下：

| 场景 | 是否重新选路 | 是否增加临时预留 | 会话映射如何处理 |
|---|---:|---:|---|
| 老会话，原实例可用且低于阈值 | 否 | 否 | 保留原目标，并重新计算 30 分钟有效期 |
| 老会话，原实例不可用或达到阈值 | 是 | 是 | 改为新目标，并重新计算有效期 |
| 新会话 | 是 | 是 | 在存在会话标识时建立新映射 |

保持原实例的请求不会增加临时预留，因为它没有发生新的实例分配；新会话和改迁会话都会增加目标实例的临时预留。

因此，临时预留量不能理解为实例的活跃会话数，会话映射也不能直接代表当前仍在处理的请求数。前者用于短期选路补偿，后者用于后续请求保持亲和，两类状态必须分别解释。

## 四、状态采集与动态摘挂设计

动态摘挂的设计重点不是简单地“超过阈值就下线”，而是明确三个问题：**状态如何采集、阈值如何影响路由、采集失败与真实故障如何区分**。当前方案通过后台采集、被动健康检查和会话迁移共同完成状态控制，三者的职责不能混为一谈。

### 4.1 采集链路：后台更新状态，请求只读取结果

OpenResty 的每个工作进程启动后，都会创建一套后台采集任务。采集过程按以下方式运行：

1. 首次任务立即执行，依次检查所有 vLLM 实例；
2. 每个实例通过独立的监控接口获取数据，单次请求最多等待 300 毫秒；
3. 本轮检查全部完成后，等待 1 秒再开始下一轮。

### 4.2 负载指标：以运行请求数驱动当前选路

后台任务从 vLLM 提供的 Prometheus 监控数据中，提取当前正在处理的请求数量，并将结果写入共享负载状态，供后续选路使用。

在当前设计中，运行请求数既是实例间比较负载的基础，也是后台动态摘挂的判断依据；临时预留量则用于补偿采样间隔内的新分配请求。

### 4.3 阈值控制：分离请求选路与实例摘挂

每个实例都设置了运行请求数阈值，当前统一为固定值。成功采集指标后，系统按照以下规则调整实例状态：

- **运行请求数达到或超过阈值**：将实例标记为不可用，后续选路时跳过；
- **运行请求数低于阈值**：将实例恢复为可用，重新参与后续分配。

动态摘挂与请求选路中的阈值判断形成了两层控制：

| 控制位置 | 判断依据 | 设计目的 |
|---|---|---|
| 请求选路 | 运行请求数＋临时预留请求数是否达到阈值 | 防止老会话继续粘到高负载实例 |
| 后台采集 | 实际运行请求数是否达到阈值 | 决定实例是否参与后续分配 |

两个判断使用的数据并不完全相同。一个实例可能因为临时预留量较高而触发老会话迁移，但它的实际运行请求数尚未达到阈值，因此后台任务不会将其标记为不可用。排障和调参时，不能把“会话发生迁移”直接等同于“实例已被摘除”。

### 4.4 故障语义：区分采集失败、过载与转发异常

当后台任务无法访问某个实例的监控接口时，当前实现只记录错误，不会立即将该实例标记为不可用，也不会为上一次采集到的负载数据设置过期时间。

实例连接故障主要由被动健康检查处理：系统根据实际请求转发过程中出现的失败进行统计，并在达到失败条件后调整后端状态。

因此，当前系统同时存在三套相关但不同的机制：

| 机制 | 触发依据 | 主要影响 |
|---|---|---|
| 主动负载控制 | 监控指标中的运行请求数是否达到阈值 | 控制实例是否参与后续请求分配 |
| 被动故障检查 | 实际转发过程中是否连续失败 | 识别连接或后端服务异常 |
| 会话迁移 | 原实例不可用，或综合负载达到阈值 | 更新会话映射，将后续请求分配到其他实例 |

需要特别区分：**监控采集失败，不等于实例已经被摘除。**实例可能只是因为监控接口异常而无法更新负载，真实推理服务仍然可用；也可能已经发生故障，但要等待被动健康检查发现。

同样，实例显示为不可用时，仅凭这一状态无法判断它是因过载被主动摘除，还是因转发失败被被动摘除。排障时需要结合实例负载、可用状态和错误日志一起判断。

## 五、架构落地顺序与设计检查

大模型负载均衡不宜一次性引入所有复杂能力。更稳妥的设计方式，是先建立可验证的静态基线，再根据流量特征和实际瓶颈逐步增加负载感知、会话亲和与高级路由能力。

### 5.1 推荐的架构演进顺序

可以按照以下顺序完成方案设计与落地：

1. **明确目标**：先确认多实例要解决的是吞吐、可用性、滚动升级，还是兼而有之；
2. **划分实例池**：按模型兼容性和故障域组织后端实例；
3. **统一状态采集**：建立健康状态与负载状态的采集机制；
4. **建立静态基线**：先用轮询或最少连接验证多实例转发；
5. **引入负载感知**：在基线之上加入 `running + waiting + reserved`；
6. **增加会话亲和**：多轮前缀复用收益明显时，再引入会话映射；
7. **定义异常行为**：明确全忙、全故障和超时重试的处理方式；
8. **补齐入口高可用**：建设双 LB 主备，并保护滚动升级中的流式请求；
9. **评估高级架构**：规模与收益明确后，再引入 KV-aware 路由或 PD 分离。

这一顺序的核心是：**每一步都解决一个已经识别的问题，并为下一步保留可验证的状态与指标。**

### 5.2 设计评审的五个关键问题

方案落地前，可以用以下五个问题检查架构是否完整：

1. **流量是否真的有状态？**  
   单轮、短请求为主时，不必一开始维护复杂会话映射；多轮对话和 Agent 场景则需要认真设计缓存亲和。

2. **路由依据是否反映真实压力？**  
   只看请求数和 `running` 都不够，至少要理解排队、新请求预留和指标新鲜度。

3. **故障是否会被误判为空闲？**  
   任何指标缺失、解析失败和采集超时都必须有独立状态，不能默认填零。

4. **重试是否可能重复执行？**  
   默认保护生成请求和 Agent 请求，只对有明确语义的失败进行有限重试。

5. **新增复杂度是否有可量化收益？**  
   会话共享状态、多活路由、专用 KV-aware 控制面和 PD 分离都应在确有需要时引入，而不是作为架构起点。

### 5.3 最终验收标准

高并发能力不等于“所有实例都在线”，而是：**请求能够被分配到合适的实例，异常状态不会被误读，过载不会引发重试风暴，故障时服务仍能按预期降级。**
